## 1. 製品定義

GitPeek は**作者専用の Git ビューワー**である。コミット操作は一切行わない。

作者は git を CLI で操作する派であり、GUI からコミットする意思がない。したがって本アプリは
「git の書き込み操作を GUI に持ち込む」方向には一切拡張しない。これは機能の不足ではなく、
**明示的な設計上の境界**である。

主用途は次の2つ:

- **(a) 自分が書いていないコードを読む** — OSS、上流リポジトリ、他人の変更
- **(b) 複数リポジトリの状況を横断的に把握するダッシュボード**

git に対して書き込みを行うのは **checkout / fetch / fast-forward マージ / clone** の4つのみ。

### 1.1 恒久的に非対象とするもの

以下は「まだ作っていない」のではなく「作らないと決めた」ものである。

| 非対象 | 理由 |
|---|---|
| あらゆるコミット操作（commit / amend / rebase / cherry-pick / revert） | 製品定義そのもの |
| stage / unstage / discard / stash の作成・適用 | 作業ツリーは read-only。ビューワーが未保存作業を壊す経路を構造的に断つ |
| `--force` 付き checkout、自動 stash | 同上 |
| 非 fast-forward マージ | 競合解決 UI を持たない以上、中途半端に着手すべきでない |
| shallow clone (`--depth`) | 履歴グラフの閲覧が目的であり、浅いクローンは本末転倒 |
| サブモジュールの**自動**取り込み | 黙って別リポジトリを取ってこない。clone の確認画面でチェックされたときだけ取り込む（2026-09-05 に利用者の判断で追加。§8.4）|
| 自動更新、コード署名 | 配布先が作者のみ。運用コストが見合わない（署名は 2026-09-08 に調べ直した。§2.3.4）|
| Gravatar 等の外部通信 | オフライン動作とプライバシーを損なう |

**10 万コミット超のモノレポはここに含めない。** v1 の設計（全件をメモリに載せてフロントへ渡す、
§4.1）と両立しないだけで、作らないと決めたものではない。**100 万コミット級の正式対応は
v1.1 以降で行う**（task_lists.md の「v1.1」表）。v1 では自動で読みに行かず、明示的に
選ばれたときだけ読む（§4.1）。

## 2. 技術スタックと配布

### 2.1 スタック

- **Tauri v2**（Rust バックエンド）＋ **React + TypeScript + Vite**（フロントエンド）
- コミットグラフは**自前のレーン計算 + SVG 描画**。既製グラフライブラリは不採用。

### 2.2 「美しいコミットグラフ」を最優先した結果としての選択

本アプリを作る第一の動機は「コミットグラフを美しく表示すること」である。この一点から
形態と描画方式を逆算した。

グラフの美しさを決めるのは次の3点である。

1. 任意の曲線を高 DPI で滲まずに引けるか
2. ホバー / クリックの当たり判定が安く取れるか
3. ライト / ダークのテーマ切替が容易か

**SVG はこの3点をすべて無料で満たす。** ベジェ曲線、CSS 変数によるテーマ切替、DOM イベントに
よる当たり判定がそのまま使える。

- **Canvas** は描画こそ速いが、DPI 対応・当たり判定・テキストをすべて手書きになる。しかも
  数万コミットあっても実際に描画するのは可視範囲の数十行だけなので、速度の利点が効かない。
- **WebGL** は過剰。
- **TUI** は文字グリッドであり、曲線が原理的に引けないため失格。
- **ネイティブ GUI（WinUI / Qt）** は描画自体は可能だが、シンタックスハイライト付き差分と
  AI の Markdown 出力を綺麗に出すエコシステムが Web に比べて著しく弱い。
- **VS Code 拡張**は「エディタを開いている」前提が必要になるため、作者の希望により除外。

容器として Electron ではなく **Tauri v2** を選んだ理由。

- 配布サイズが1桁 MB（Electron は 100MB 超）
- 常駐メモリが Electron の 1/3〜1/2。複数リポジトリを常時監視する性質のアプリでこれが効く
- Rust 側で git サブプロセスの並行実行とストリーミング出力の扱いが素直
- 環境が完全に揃っている（§2.4）

既製グラフライブラリ（`@gitgraph/js` 等）を採らない理由。これらは自前のレイアウトと描画を
抱えており、仮想スクロールおよび「レーン割り当てを自分で制御する」という本アプリの中核要件と
正面から衝突する。

### 2.3 アプリ識別と配布

- アプリ名: **GitPeek**
- bundle identifier: **`com.tatsu.gitpeek`**
- `productName`: `GitPeek`、ウィンドウタイトル: `GitPeek — <リポジトリ名>`
- 配布は**ポータブル zip のみ**

> **注意**: Tauri v2 の bundler が Windows 向けに吐けるターゲットは `nsis` と `msi` だけで、
> **zip ターゲットは存在しない**。したがって「ポータブル zip」は `tauri build` が生成する
> `src-tauri/target/release/GitPeek.exe` を自前で zip 化する手順になる。単一 exe で動作する
> （WebView2 Runtime はシステム側にインストール済みのものを使うため同梱不要）。
> この zip 化は npm script として用意する。

**`tauri.conf.json` の `mainBinaryName` を消さないこと**（T-26）。これが無いと cargo の
パッケージ名がそのまま出て、**実体は `gitpeek.exe`（小文字）**になる。それでも `package:zip` は
通る — Windows が大文字小文字を区別しないためで、**偶然通っているだけ**。zip の中の名前も
PowerShell が指定どおりの綴りで書くので、**壊れたことに気付けない。**

- 自動更新（Tauri updater）は入れない
- コード署名しない（初回起動時に SmartScreen 警告が出るが「詳細情報 → 実行」で通す。理由は §2.3.4）

#### 2.3.1 `Givsoner` からの改名（2026-09-06）

**T-25 まで、このアプリの名前は `Givsoner`、identifier は `com.tatsu.givsoner` だった。**
2026-09-06 に利用者が `GitPeek` へ改名すると決めた（T-28）。

**identifier も `com.tatsu.gitpeek` へ変えた。移行コードは書いていない。**
identifier は表示名ではなく保存先の鍵なので、リブランドしても据え置くのが普通であり、
その案も含めて 3 つ並べて聞いた。利用者が「変えて入れ直す」を選んだ。

そのため改名をまたぐと、**保存先が変わる**:

| いま | 中身 |
|---|---|
| `%APPDATA%\com.tatsu.givsoner\` | 改名前の `settings.json` / `state.json` / `skills\` / `reviews\` / `logs\` |
| 資格情報マネージャーの `com.tatsu.givsoner` | 改名前の API キー |

**どちらもアプリからは消さない**（利用者のデータを黙って消さない。CLAUDE.md §1 に倣う）。
要らなくなったら利用者が手で消す。**一度しか動かない移行経路を永久に抱えるより、
入れ直すほうが安い**という判断であり、v1 前で利用者が 1 人だから通る判断でもある。

#### 2.3.2 リリース（2026-09-07）

**配布先は GitLab の Releases**（`https://gitlab.com/tatsunoko7324/gitpeek`）。**exe そのものは
Release に添付できない**ので、zip を**汎用パッケージレジストリ**（generic packages）へ上げ、
Release からはそのリンクを張る。公開プロジェクトなので、落とす側にログインは要らない。

**CI では作らない。** GitLab.com の共有ランナーに Windows のものが無く、Tauri の Windows 向け
ビルドを Linux で作るのは現実的でないため、**手元でビルドして手元から上げる**
（`scripts/release.ps1` / `npm run release`）。将来 Windows のランナーを用意する気になったら、
同じ API を CI から叩けばよい（`JOB-TOKEN` に変えるだけ）。

スクリプトが**実行前に止まる条件**は次の 4 つ。どれも「あとから直せないもの」を作らないためにある。

| 止まる条件 | 理由 |
|---|---|
| `GITLAB_TOKEN` が空 | **トークンはスクリプトにもリポジトリにも置かない。** 環境変数から読むだけ |
| 追跡ファイルに変更が残っている | zip の中身が push 済みのコードと食い違う |
| HEAD と `origin/master` が違う | 誰も取得できないコミットからリリースを作らない |
| タグが既に origin にある | 同じバージョンで中身の違うものを 2 つ作らない |

**タグは GitLab 側で作る**（`ref` にコミット SHA を渡す）。手元でタグを打ってから上げると、
リリースの作成に失敗したときにタグだけが残る。手元へは `git fetch --tags` で持ってくる。

**プロジェクトが公開でも、パッケージレジストリは既定で匿名に開いていない**
（2026-09-07 に実測。匿名の HEAD が 401 を返した）。**Settings → General → Visibility, project
features, permissions → Package registry →「Allow anyone to pull from Package Registry」**を
ON にして初めて、ログインしていない人が zip を落とせる。**既定は OFF。**
リンクはあるのに落とせないリリースができるので、**スクリプトは公開したあとに匿名で HEAD を
投げて確かめ**、落とせなければ設定の場所を出す（リリースは作り直さなくてよい）。

**`.ps1` は UTF-8 BOM 付きで保存する。** Windows PowerShell 5.1 は BOM の無い `.ps1` を
ANSI（この環境では CP932）として読むので、**日本語のコメントが化けて閉じ引用符まで飲み込まれ**、
`The string is missing the terminator` で落ちる（2026-09-07 に実際に踏んだ）。

#### 2.3.3 アイコン（2026-09-08）

**Tauri のロゴをそのまま配っていた**（`tauri init` が置いたもの）。他人向けの README に
そのロゴが出ている状態でもあったので、独自の図案へ差し替えた。

図案は**コミットグラフのレーンと目**を重ねたもの。色はアプリから採ってある

- **元画像は `docs/images/app-icon.png`**（1024×1024 の透過 PNG）。ここから
  `npm run tauri icon docs/images/app-icon.png` で全サイズを作る
- **`icons/android` と `icons/ios` は追跡しない**（Windows 専用なので使わない。`.gitignore`）
- **16px では目が潰れる。承知のうえで通した** — 小サイズ専用の簡略版は作っていない。

#### 2.3.4 コード署名をしない理由（2026-09-08 に調べ直した）

**v1 でも署名しない**（§1.1 の判断を維持）。技術は簡単で、`tauri.conf.json` の
`bundle.windows.certificateThumbprint` か `signCommand` を足せば `package:zip` の中で署名される。
**難しいのは手続きと費用、そして「払っても警告が消えるとは限らない」ことのほう。**

| 手段 | この条件（日本・個人）で | 警告 |
|---|---|---|
| Azure Artifact Signing（旧 Trusted Signing）| **使えない** — 公式ドキュメントで**個人開発者は米国・カナダ在住に限る**（法人なら日本も対象国）| — |
| 商用 CA の個人向け証明書 | 使える。年 1〜3 万円 ＋ USB トークン（2023-06 以降、鍵は HSM 必須）| **すぐには消えない**（評判が貯まるまで出続ける）|
| EV 証明書 | **法人のみ** | 即時 |
| Microsoft Store（MSIX）| 使える。個人登録は一回払い | **出ない**（Store が署名する）|

**個人 OV では SmartScreen の警告が残る公算が大きい**ので、費用に対して得るものが小さい。
いまの代替（**SHA-256 の掲示 ＋ 越え方の明記**）のほうが、落としたものが本物かを確かめられる
ぶん誠実でもある。将来「知らない人へ配る」段になったら **Store 経由**が第一候補。

やることになった場合も、**「禁止をやめる」のではなく「証明書が用意されているときだけ署名する」**
という条件付きにする（CLAUDE.md §1 の緩め方に倣う。証明書が無い環境でビルドが落ちないこと）。

## 3. git 実行方針

### 3.1 全 git 呼び出しに固定付与するオプション

```
git -c core.quotepath=false \
    -c core.autocrlf=false \
    -c core.pager=cat \
    -c color.ui=false \
    -c core.commitGraph=false \
    -C <repo> <subcommand> ...
```

| オプション | 理由 |
|---|---|
| `core.quotepath=false` | **未指定だと日本語ファイル名が 8 進エスケープされて返る。** 実測でこの環境は未設定＝デフォルト `true` であることを確認済み。付け忘れると日本語パスが全滅する |
| `core.autocrlf=false` | ユーザーの `.gitconfig` に左右されない決定的な挙動を得る |
| `core.pager=cat` | pager がサブプロセスで起動して固まるのを防ぐ |
| `color.ui=false` | ANSI エスケープが出力に混入するのを防ぐ |
| `core.commitGraph=false` | **本アプリの読み方では commit-graph が遅い**（下記） |

#### commit-graph を無効にする理由

commit-graph は「メッセージを読まずに履歴をたどる」操作のための索引である。ところが
GitPeek の主問い合わせ（§4.1 の全件ダンプ）は `%an`/`%ae`/`%s` を含むため、**どのみち
コミットオブジェクトを 1 件ずつ読む**。commit-graph を有効にすると、そこへ別ファイルへの
アクセスが上乗せされるだけになる。

Linux カーネル（1,481,526 コミット / pack 6.6GB）で、同一マシン・同一コマンドの A-B 計測:

| `core.commitGraph` | `git log --branches --remotes HEAD --topo-order -z --format=…` |
|---|---|
| `true` | 59.5 秒 |
| `false` | 19.0 秒 |

ahead/behind はメモリ上のグラフから計算する（§4.5）ので、commit-graph が本来効く
`rev-list --count` 系はそもそも呼ばない。**git は `gc` の際に commit-graph を自動生成する**
ため、明示的に切っておかないと、ある日を境に 3 倍遅くなる。

なお `%h`（短縮 SHA）の有無と `--topo-order` の有無は同じ計測で有意差が無かった
（`%h` を外して 16.7 秒、`%H` だけなら 14.6 秒）。**全件ダンプの時間はほぼコミットオブジェクトの
読み取りそのもの**であり、書式を削っても縮まない。

### 3.2 全 git 呼び出しに設定する環境変数

```
GIT_TERMINAL_PROMPT=0
GIT_SSH_COMMAND=ssh -o BatchMode=yes
```

**`GIT_TERMINAL_PROMPT=0` は必須である。** これが無い場合、認証が必要な場面で git は端末から
入力を読もうとする。GUI から起動した子プロセスには端末が無いため、**無言でハングする**。
`0` を設定すると `could not read Username for ... terminal prompts disabled` で即座に失敗するので、
アプリ側でエラーを整形して見せられる。

SSH も同様に、`BatchMode=yes` が無いとパスフレーズ入力待ちでハングする。

### 3.3 認証

認証は **git CLI に完全委譲**する。アプリはパスワードも Git のトークンも一切扱わない。

この環境では `credential.helper=manager` が設定済みで、GUI から `git clone https://...` を
起動すると Git Credential Manager が自前のウィンドウ（GitHub なら ブラウザ OAuth）を出し、
Windows 資格情報マネージャーにキャッシュする。2回目以降は無人で通る。

読み取りをライブラリ（gix / git2-rs）ではなく CLI に統一した最大の理由がこれである。
ライブラリを使うと認証・プロキシ・`.gitconfig` の全設定を自前で再実装する羽目になる。

### 3.4 git の検出と前提条件

- PATH の `git` を既定とし、設定でフルパス指定も可能
- **最低バージョン 2.20** を要求（現環境は 2.43）
- 未検出時は専用画面（公式インストーラへの導線＋パス手動指定欄＋再チェックボタン）

### 3.5 透明性 — git コマンドログ

**「git コマンドログ」パネルを常設する。** 実行した全コマンド・exit code・stderr・所要時間を
時系列で表示する（直近 500 件のリングバッファ、**リポジトリ切替でクリアしない**）。

**「常設」は「畳めない」という意味ではない。** 出し入れの口は**設定の「一般」1 か所**だけで
（T-25。2026-09-06 に利用者が決めた。ヘッダのボタンは畳んだ）、**状態は `settings.json` に残る**
（`ui.showCommandLog`。既定は出す）。畳んだまま再起動しても戻らないので、
**ヘッダのボタンを復活させないこと** — 入口が 2 つに戻る。畳んでいるのは不具合ではない。

理由。作者が git CLI 操作派である以上、「このアプリが裏で何を実行したか」が完全に見えることが
信頼に直結する。ビューワーがブラックボックスで git を叩くのは、この用途で最も嫌われる性質である。

エラー表示は常に「人間向けメッセージ ＋ 展開すると生 stderr」の2段構えとする。

**記録先は `commandlog::LogSink` として抽象化する**（T-02 で決定）。本番は `EmittingLog`
（リングバッファへ積み、`command-log` イベントでフロントへ送る）、テストは `CommandLog` を
そのまま渡す（積むだけ）。こうすると `git/exec.rs` が Tauri に依存せず、git を実際に起動する
結合テストが `AppHandle` 無しで書ける。`tauri::test::mock_app()` は Windows で
WebView2 の解決に失敗して使えなかった。

### 3.6 異常系

| 状況 | 扱い |
|---|---|
| 登録リポジトリのパスが消えている | 一覧でグレーアウトし「再指定 / 登録解除」を提示 |
| `.git/index.lock` が残留 | 検出して「他の git プロセスが動作中の可能性」を明示。**アプリ側から絶対に削除しない** |
| bare リポジトリ | 閲覧のみ許可し、checkout を無効化 |
| shallow クローン | 正常に表示（履歴が浅いことを明示） |
| detached HEAD | 正常表示 |
| コミット 0 件の空リポジトリ | 正常表示（空状態） |

## 4. データ取得とグラフのアーキテクチャ

### 4.1 全件一括取得

リポジトリ選択時に**全コミットのメタ情報のみを一括取得**し、**Rust 側でレーン計算まで確定**する。
フロントエンドの仮想スクロールは「確定済み配列の可視範囲を DOM 化する」役割に限定する。

差分・コミット本文・ファイル内容は選択時に遅延取得する。

**なぜページングではなく全件なのか。** 正確な topo-order グラフを描くには、原理的に
「対象 ref から到達可能な全コミットの親子関係」が事前に必要である。200 件ずつの増分読みでは、
後から現れた親でレーン割り当てが遡って変わり、**描画中にグラフが踊る**。グラフの美しさが本アプリの
存在理由である以上、これは許容できない。

**コスト見積。** 1 コミットのメタ情報は約 200B。3 万コミットで約 6MB、`git log` 自体も 3 万件で
数百 ms 〜 1 秒程度。十分現実的である。

この設計の帰結として、**v1 の想定規模は数万コミット / 数千ファイルを上限**とする。10 万コミット超の
モノレポは **v1 では非対象**（恒久的な非対象ではない。§1.1）。永続インデックス DB は持たない
（v1 の規模に対して複雑さが見合わない）。

非対象の側がどうなるかの実測（Linux カーネル 1,481,526 コミット / pack 6.6GB、リリースビルド）:

| 内訳 | 時間 |
|---|---|
| `git log` の実行と読み取りとパース | 17.4 秒（うち git 自体が約 16 秒） |
| JSON 直列化（450MB） | 0.7 秒 |
| 2 回目（ref の指紋が一致 → キャッシュ） | 0.13 秒 |

**時間のほぼ全部が git 自身**であり、こちら側の工夫では縮まない。

**450MB を IPC で webview へ渡す構造の方が、実は苦しい。** デバッグビルドでの実測で、
フロント側から見た往復は 39.7 秒（うち `git log` は 15.7 秒）。差の約 24 秒は直列化と転送と
`JSON.parse` であり、**その間 webview のメインスレッドは止まる**（ウィンドウが白いまま
描画されない時間が生まれる）。読み終えた webview は 1.5GB を保持する。

100 万コミット級を実用範囲に入れるなら「全件をフロントへ渡す」前提（本節）ごと見直しが要る。
**この見直しは v1.1 以降で行う**（task_lists.md の「v1.1」表）。v1 では見直さず、
**時間がかかっていることが分かる表示**で凌ぐ（§4.6）。

見直しの方向（v1.1 で詰める。ここでは決めていない）:

- レーン計算まで Rust 側で終える現状の構造を活かし、**フロントへ渡すのを可視範囲だけにする**
  （全件の JSON 直列化と `JSON.parse` が消える）
- コミットのメタ情報を Rust 側で持ち続け、行の取得をコマンド越しのページングにする
- 永続インデックス DB を持つかどうかは、上の 2 つで足りるか測ってから決める

**ただし非対象の規模を黙って読みに行かせない。** 148 万コミットのリポジトリを開いたまま
アプリを終了すると、次回起動時に自動で読み込みが走り、デバッグビルドで 60〜90 秒
操作できなくなったうえ、**gitpeek.exe が 3.5GB・WebView2 が 3.2GB まで伸びて
プロセスが消えた**（エラー出力なし。空き物理メモリは 10GB 以上あった）。

そこで、**前回の件数が 10 万コミットを超えるリポジトリは自動で読み込まない**。
件数と所要時間の見込みを出し、明示的に選ばれたときだけ読む
（`src/store/snapshot.ts` の `LARGE_REPOSITORY_COMMITS`）。前回の件数が無い初回だけは
判断材料が無いので素直に読みに行く — 分母を得るのに `rev-list --count` を呼ぶと
`git log` と同じだけ待つことになり、本末転倒だからである。

なお**デバッグビルドでは JSON 直列化だけで 17.7 秒**かかる（リリースの約 28 倍）。
`npm run tauri dev` で測った数字をそのまま製品の性能と見ないこと。
リリースビルドで動かすには `npm run start:release`。

キャッシュは HEAD と全 ref の SHA をキーに無効化する。直前のリポジトリのグラフは LRU で 2〜3 件
保持し、切替を体感即時にする。

### 4.2 起点 ref — `--all` を使ってはいけない

グラフの起点は**全ローカルブランチと全リモート追跡ブランチ**、および HEAD とする。
**タグは起点 ref に含めない**（どのブランチからも到達不能な古いタグが孤立点として散らばるのを防ぐ）。

> **重要**: `git log --all` は「`refs/` 配下の全 ref、および HEAD」を起点にする。これは
> **`refs/tags/` も `refs/stash` も `refs/notes/` も含む**ため、上の決定に違反する。
> 正しくは次を使う。
>
> ```
> git log --branches --remotes HEAD --topo-order ...
> ```
>
> （`--branches` = `refs/heads/*`、`--remotes` = `refs/remotes/*`）

タグはコミット上のラベルとしては表示する。**タグの指すコミットが読み込み集合に含まれない場合**
（ブランチが消された古いリリースタグなど）は、タグツリーには表示するが「グラフ外」と印を付け、
ジャンプを無効化する。

### 4.3 並び順

**topo-order 既定 / date-order に切替可**。

切替時は `git log` を再実行しない。全コミットの親子関係と日時がメモリにあるため、
**メモリ上で並べ替えとレーン再計算のみ**で済む（数十 ms）。
date-order 表示時は「この表示では線が交差します」の注記を出す。

### 4.4 ブランチ表示 ON/OFF の意味論

チェックを外したブランチについて、**可視 ref 集合から到達可能集合を再計算してレーンを振り直す**。
行数も線の本数も実際に減る。

淡色化やラベル非表示ではなく再計算にした理由。解決したい痛みは「リモート追跡ブランチが 40 本
あって画面が線だらけ」であり、線の本数が減らなければ目的を達成しない。全コミットがメモリ上に
あるので、再計算は数万コミットでも数十 ms で済む。

プリセット: 全選択 / 全解除 / ローカルのみ / リモートのみ。選択状態はリポジトリごとに永続化する
（`settings.json` の `repositories[].visibleRefs`）。

**起点にするのはブランチと HEAD だけ。** タグは起点 ref にしないので（§4.2）、
タグのチェックはグラフの中身に影響しない。**HEAD は常に起点に入れる** —
`git log --branches --remotes HEAD` と揃えるためで、全部のチェックを外しても
今いる場所の履歴だけは残る（画面が空になるより手掛かりが残るほうがよい）。

**幹の ref を隠した場合も lane 0 は空けない。** 起点が絞った集合に残らなければ、
レーン計算は先頭コミットを幹として扱う（§5.1-1）。lane 0 を空けたままにすると
グラフ全体が 1 レーン右へずれる。

**タグにはチェックボックスを置かない**（T-10 で決定）。タグは起点 ref ではないので、
チェックを外してもグラフは 1 行も変わらない。「押せるが何も起きない」ほうが、
最初から無いより分かりにくい。タグはツリーに出すが、操作はジャンプとコピーだけにする。
`visibleRefs.excluded` にタグの ref 名が入ることは無い。

**絞り込みの結果はコミットリストの行数にも出る。** グラフだけを絞ってリストが全件のままだと、
行の文字と線が 1 行ずつずれる（§6.3）。

### 4.5 ahead/behind

**全ブランチの ahead/behind をメモリ上のグラフから計算する。**

`git rev-list --count` をブランチ数だけ呼ぶ実装だと、100 ブランチで 100 プロセス起動になる。
§4.1 で全コミットの親子関係を保持しているので、到達性計算で無料で求まる。

**比べる相手は上流**（`git branch -vv` と同じ）。上流の無いローカルブランチ、
リモート追跡ブランチ、タグは相手が決まらないので数値を出さない。
上流が `fetch --prune` で消えている場合も同じ。

数え方は**両側から同時に親へ下り、共通祖先に着いた時点で止める**。全体を舐めないので、
分岐が浅いほど速い（ふつうのブランチと上流の差は数コミット）。
ref ごとにビットセットを持つ実装は 20,000 コミット × 数千 ref でメモリが厳しいので採らない。

### 4.6 途中経過の見せ方

想定規模（数万コミット）では読み込みは 1 秒未満で終わる。**非対象の規模でも「固まった」と
思わせない**ことだけを目的に、途中経過を出す。

段階は取得の内訳そのもの。`Refs`（ref 一覧と HEAD）→ `Commits`（`git log` の全件ダンプ）→
`Graph`（到達可能集合と幹の決定）→ `Transfer`（直列化と転送）。

- **件数は `git log` の出力を読みながら NUL を数えて得る。** パースの完了を待たない。
  そのために `exec::run_streaming` があり、`Command::output()` と違って完了前に読み進める
- **割合の分母は前回の読み込み件数**（`state.json` の `lastCommitCount`）。初回は分からないので
  割合を出さず件数だけ流す。**嘘の割合を出すより、進んでいることが分かる方を採る**
- 報告は 150ms 間隔に間引く。300MB を 64KB ずつ読むと 5000 回近く呼ばれるため
- 表示は 400ms 経ってから出す。数万コミットではバーが一瞬光って消えるだけになる
- `Transfer` は**イベントを送ってから**返す。この段階で webview のメインスレッドは
  止まるので、止まる前に「何をしているか」を出しておく必要がある

進捗の受け口は §3.5 の `LogSink` と同じくトレイト
（`git::progress::ProgressSink`）にし、git 側のコードを `AppHandle` に依存させない。

## 5. コミットグラフの視覚仕様

### 5.1 レーン割り当てアルゴリズム

グラフの美しさの 8 割はここで決まる。

1. **lane 0 を幹に予約する。**
   既定ブランチ（`origin/HEAD` → 無ければ `main` / `master` → 無ければ現在の HEAD の順で決定）の
   第一親チェーンを lane 0 に予約し、**必ず一直線に描く**。
   幹が画面左端をまっすぐ通り、他がすべて枝として見えるため、可読性が劇的に上がる。

   **幹は起点より新しい側へも伸ばす。** 起点を第一親に持つ子を辿り、分かれ道では
   topo-order で先に来る子（画面で上に描かれる方）を採る。第二親でしか繋がらない子は
   幹にしない（マージで合流しただけの枝まで引き込むと lane 0 が枝へ乗り移る）。

   下方向だけを幹にすると、**既定ブランチより先へ進んだブランチを開いているときに
   画面上部が壊れる**。実測（AerialSoldierMaker、master より 9 コミット先の
   ブランチを checkout した状態）では、一直線の履歴にもかかわらず上 9 行が lane 1 を下り、
   master の行で lane 0 へ折れた。1 本の線が途中で折れているようにしか見えない。

2. **レーン再利用は最小空きレーンだが、解放直後の 1〜2 行は再利用を保留する。**
   即座に最小番号を再利用すると、1 本の線が交差直後に無関係なブランチへ「化ける」ように見える。
   逆にブランチが尽きるまで占有し続けるとレーン数が増えすぎる。その中間を取る。

   **ただしルートコミット（親なし）で終わったレーンは二度と配らない。**
   レーンの終わり方は 2 通りある。マージや「同じ親を待つレーンへの畳み込み」で終わる場合は、
   線が別レーンへ曲がって続くので、そこで終わったことが目に見える。**ルートだけは線が
   その場で止まる。** 数行後に同じレーンを別の枝が使うと、レーン色は同じなので
   **1 本の線が穴を空けて続いている**ようにしか見えない。
   実測（onyx、orphan ブランチ `origin/assets/...` のルート）では 2 行後に再利用されており、
   目視で「グラフが途中で切れている」と報告された。

   費用はほぼ無い。ルートはリポジトリに数個しかなく、onyx（ルート 4 個）で max_lane が
   49 → 52 に増えるだけで、同時レーン数の平均は 11.43 のまま変わらない。
   vite（ルート 1 個）と drogon（同）では**何も変わらなかった**（元々再利用されていない）。

3. **マージコミットの第 2 親は右側に新レーンを起こす。**

4. **レーン数に上限を設けない。**
   レーン幅を可変にして詰める方式は、密度が上がったときに確実に破綻する。

   **グラフは幅を持つ「列」として扱い、列幅より右のレーンは切る**（既定 200px、
   ドラッグ可変、リポジトリごとに `state.json` へ永続化）。全レーンぶんの幅を常に
   空けると本文が画面の外へ押し出される（onyx は 49 レーン ＝ 712px あった）。
   見出しの取っ手を引けば全レーンまで広がる。**横スクロールはリスト全体で 1 つ**にする
   （グラフ列だけ別にスクロールさせると行とずれる）。

### 5.2 描線と配色

- **線**: 垂直の直線を基本とし、**分岐 / 合流点のみ角丸ベジェ**
  （直角エルボーや斜め直線ではなく、最も柔らかい形状を選ぶ）。
  **曲がりに使う縦の長さは横の移動量に合わせて伸ばす。** 1 レーンぶんの移動では 8〜12px の
  角丸に相当する長さ（実装は `CORNER_RADIUS * 2` を下限とする）、それ以上またぐときは
  移動量と同じだけ縦を使う。固定長にすると、数レーンぶんの移動が 20px の帯に押し込まれて
  ほぼ水平の直線になる（onyx の実データで、1 行のあいだに 8 レーン移動する辺が 99 本あった）。
- **線は辺だけで描く。** 素通りするレーンの縦線を辺と重ねて引いてはいけない。
  素通りするレーンは必ず「上の行のノードから下の行の親まで」の辺に覆われているので、
  重ねると、辺が曲がって別レーンへ移った後に縦線だけが残り、**どこにも繋がらない
  線の切れ端**になる。仮想スクロールで窓が途中から始まる場合は、窓を跨ぐ辺を拾うこと。
- **走る余地の無い中間レーンは経由しない。** 第 2 親のために起こしたレーンが 1〜2 行で
  終わる場合（同リポジトリで 137 箇所）、そのレーンまで右へ跳ねてすぐ左へ戻る弧になり、
  グラフから飛び出して見える。縦に走る区間が無いレーンは通らず、直接繋ぐ。
- **配色**: レーン番号で **8 色をローテーション**。ただし **lane 0（幹）のみ無彩色寄りの固定色**に
  して幹を主張させる。パレットは彩度を抑え、ライト / ダークで別定義する。

  ブランチ名のハッシュで色を決める方式は不採用。§5.1-2 のレーン再利用と組み合わせると
  隣接レーンに似た色が並ぶ事故が起きやすく、結果的に汚くなる。

  **パレットの並び順は隣接レーンの色差で決める。** 隣り合う 2 レーンは配列上も隣り合う
  2 色になるので、順番を入れ替えるときは CIE Lab の色差がどの隣接組でも 60 以上あることを
  確かめること（T-08 の実測: olive と brown を隣に置くと 25.7 まで落ちて見分けがつかない）。

  **明るさはライトとダークで別々に決める。同じ色を使い回さない。** 白地に濃い色を置くと
  線が重く、グラフ全体が暗く沈む（T-08 の目視で指摘された）。ライトは **L\* 55〜60 /
  白との輝度比 3.1〜3.7**、ダークは **L\* 62〜74 / 背景との輝度比 5.7〜8.1** に揃える。
  ライト側の輝度比の下限は 3.0（WCAG 1.4.11 の非テキスト要素）。ホバー行の背景
  (#e7ebf1) の上でも 2.6 を切らないこと。**これ以上明るくすると線が見えなくなる**ので、
  「まだ暗い」と感じたら色ではなく線幅を疑う。

- **ノード**: 通常 = 直径 8px の塗り円 / マージ = 中空円 / HEAD = リング付き / 選択中 = 拡大＋発光 /
  **ルート（親なし）= ノードの下に短い横棒**。レーンの終わり方のうち、マージと
  「同じ親を待つレーンへの畳み込み」は線が別レーンへ曲がって続くので終わりが目に見えるが、
  **ルートだけは線がその場で止まる**。印が無いと「終わった」のか「切れた」のか分からない
  （§5.1-2）。横棒は行の高さとレーン幅の内側に収めること。はみ出すと隣の線を横切って見える
- **寸法**: 行高 28px、レーン幅 14px、ノード列の左マージン 12px（実装後に微調整）

### 5.3 ナビゲーション補助

**スクロールバー上に ref マーカーを描く**（ブランチ先端 = レーン色の短い線、タグ = 小さな菱形）。

数万コミットのリストではスクラバが極端に小さくなり位置感覚が完全に失われるため、
実装コストに対して効果が非常に大きい。ミニマップは作らない。

**同じ高さに重なるぶんは 1 本に束ねる。** onyx は ref が 3,790 個あり、そのまま置くと
12px の帯が塗り潰れるうえ DOM が 3,790 要素になる。トラックを固定数（300）に割り、
1 枠につき 1 つだけ描く。残すのは**ブランチ先端を優先**（タグより「今どこにいるか」の
手掛かりになる）。

## 6. UI 構成

### 6.1 レイアウト

```
+----------------+-------------------------------+----------------+
| リポジトリ一覧 |  コミットグラフ + コミットリスト| コミット詳細  |
|  (上段)        |                               |  (full message)|
|                +-------------------------------+                |
| ブランチ/タグ  |  差分本体                     | 変更ファイル   |
| ツリー (下段)  |  (side-by-side / unified)     |  一覧          |
+----------------+-------------------------------+----------------+
```

- 3 ペイン。中央だけ上下分割。境界ドラッグで比率可変、幅・比率とも永続化
  （`state.json` の `paneRatios.sidebarWidth` / `graphDiffSplit` / `commitInfoWidth`）
- 差分を side-by-side で見るには横幅が要るため、差分本体は**中央下**に置いて横幅をフルに使う
- **コミット詳細と変更ファイル一覧は右の列**に出す。**差分本体と縦に積まない。**
  積んでいたときは、詳細（本文＋作者＋親）と一覧が高さを食って差分に数行しか残らなかった。
  右へ出せば、一覧が何十行あっても差分の幅も高さも削らない
- 右の列は**縦に長い 1 列**なので、詳細は中身なり（上限つき）、一覧が残りを全部取る
- AI レビューは**さらに右のドロワー**（幅可変、閉じられる）。指摘を差分の該当行と対比しながら
  読めることが必要なため、モーダルや独立画面にしない。**開いている間はコミット情報の列と
  並べず、そちらを畳む**（3 列 ＋ ドロワーでは差分が潰れる）。
  **2026-09-06（T-23）に「入れ替える」で決着した。** ドロワーは指摘から差分の**該当行**へ
  飛べるので（§10.7.2）、閉じている間の変更ファイル一覧の役目をそのまま引き取れる。幅は
  `state.json` の `paneRatios.reviewDrawerWidth` に別で持つ（畳んだ列の幅と混ぜない）
- テーマは **OS 追従が既定**・手動切替可。作り込みはダーク優先
- UI 言語は**日本語固定**。ただし全表示文言を `src/i18n/ja.ts` に集約しキー参照する
  （i18n ライブラリは入れない。将来必要になったら差し替えるだけで済む形にしておく）

**Windows 固有**: `tauri.conf.json` の `app.windows[].dragDropEnabled` を **`false`** にする。
既定の `true` では WebView2 がファイルのドラッグ＆ドロップを先に掴み、**フロント側の HTML5
ドラッグ＆ドロップ（リポジトリ一覧の並べ替え）が一切動かない**（Tauri 本体のドキュメントに
「Disabling it is required to use HTML5 drag and drop on the frontend on Windows」と明記されている）。
引き換えに「フォルダをウィンドウへ落として登録」は使えなくなるが、v1 では非対象。

### 6.2 リポジトリ切替

- **常時サイドバー ＋ `Ctrl+P` で絞り込みジャンプ**の併用
- **タブは持たない**（1 リポジトリ 1 ビュー）。リポジトリごとに数万コミットのメタ情報をメモリに
  載せる設計と掛け算になるため。代わりに直前のリポジトリのグラフを LRU で 2〜3 件保持する
- 切替時の状態（選択コミット / スクロール位置 / ブランチ表示 ON/OFF / 開いていた差分）は復元する
- 並び順は手動 D&D ＋「最終アクセス順」表示のトグル。フォルダによるグループ分けは v1.1
- 一覧の各行に常時表示: 現在ブランチ名 / ahead・behind バッジ / dirty マーク / fetch 放置アイコン

### 6.3 コミットリスト

列構成: `グラフ | subject + ref チップ | 作者名 | 日時 | 短縮SHA`

- 列幅はドラッグ可変・永続化。列の増減は v1 では不可
- 短縮 SHA は `git log --format=%h` に委ねる（git 自身が衝突しない最短長を選ぶ）
- 日時は**既定で相対**（「3 日前」）、ホバーで絶対をツールチップ表示。設定で入れ替え可
- 作者は**名前のみ、アバターなし**。Gravatar はメールアドレスのハッシュを外部サーバに送るため、
  オフライン動作とプライバシーの両方を損なう
- ref チップが行に収まらない場合は「+N」に畳み、ホバーで全件表示。
  **チップの右クリックは行の右クリックとは別のメニュー**（T-18。§8.1）。
  畳んだぶんは対象にしない（どれを指しているか決まらない）
- ツールバーに「HEAD へ」を置く（`Ctrl+H` と同じ動作）。**checkout で HEAD が動くと
  選択行が遠くに取り残される**ので、キーを知らなくても戻れるようにする（§8.5）
- **orphan ブランチ**（幹とコミットを 1 つも共有しない履歴）の ref チップは**破線の枠**にし、
  グラフのルート終端と同じ `⊥` を前置する。判定はコミット DAG の連結成分で行う
  （親子の向きを無視した無向グラフ。到達可能性 §4.4 とは別物で union-find 1 回）。
  **マージで合流した無関係履歴は orphan ではない** — 繋がっているので線も途切れない

**列見出しは行と同じスクロールコンテナに入れ、縦だけ `position: sticky` で貼り付ける。**
外に出すと、列の合計幅が窓を超えたときに見出しだけが動かず行とずれる。さらに、見出しの
最小幅がそのまま外へ伝わって親ペインに 2 本目の横スクロールバーが生える（T-07 の目視で
両方出た）。見出しの高さは `--head-height` で固定し、仮想スクロールには `scrollMargin`
として同じ値を渡す。行の上端へ寄せるスクロールは、貼り付いた見出しの下に潜らないよう
自前で計算する（`scrollToIndex` は見出しを知らない）。

**グラフは行の背景より前面に置く。** 背面に敷くと、ホバーや選択の背景（不透明）に線が
塗り潰されて消える。`pointer-events: none` なので前面でもクリックは下の行に届く。

**並べる順と件数の正は `LaneLayout.rows`** であって、読み込んだコミット配列ではない。
レーンは可視 ref で絞られ（§4.4）、date 表示では組み替わる（§4.3）。行の文字を
コミット配列の添字で引くと、どちらの経路でもグラフと 1 行ずつずれる（T-10 で発覚）。
`rows` を順に辿り、SHA でコミットを引くこと。

### 6.4 ブランチ / タグツリー

- `feature/foo` のようなスラッシュ区切りを**階層フォルダとして畳む**
  （同一プレフィックス配下が 3 件以上で自動フォルダ化、開閉状態は永続化）
- トップレベルは `ローカル` / `リモート > origin` / `タグ` の 3 グループ
- タググループは既定で折りたたみ。ツリー上部に絞り込み入力欄を常設（ブランチもタグも同じ欄で絞る）
- 各ブランチ行に ahead/behind を表示（§4.5）
- 右クリックメニュー: checkout / 現在のブランチに FF マージ / このブランチだけ表示 /
  このブランチの先頭へジャンプ / ブランチ名をコピー / SHA をコピー

**畳む閾値は 3 件**（`refTree.ts` の `FOLDER_THRESHOLD`）。2 件のために階層を 1 段深くしても
クリックが増えるだけで、`feature/a` `feature/b` は 2 行のまま出したほうが速く読める。
数えるのは**配下（パスが 2 段以上）だけ**なので、`feature` というブランチと `feature/` フォルダが
同じ階層に並ぶことがある。ブランチがフォルダに吸われるより、両方見えるほうが正しい。
**絞り込みは畳む前に効かせる** — 1 件に絞られたフォルダは消えて平らになる。

**リモートはリモート名でグループを分け、ブランチ名からリモート名を外す**
（`origin/feature/a` は `リモート > origin` の下に `feature/a` として出る）。
`origin` 以外のリモートがあれば、その数だけグループが増える。

**ahead/behind は 0 のとき何も出さない。** 上流を持たないブランチも同じく空欄にする
（§4.5 のとおり比べる相手が決まらない）。全ブランチに「上流なし」を並べると騒がしいだけなので、
差があるときだけ `↑2` `↓3` を出し、同期しているか上流が無いかはツールチップで見せる。

**グラフから外した ref は淡色にする。** チェックボックスは小さく、遠目にはどれを外したか
読み取れない。ここでの淡色化は §4.4 が退けた「グラフの淡色化」とは別で、
グラフ側の行は実際に消えている。

**開閉状態は「畳んだ ID」を保存する**（`state.json` の `collapsedTreeNodes`、§12.3）。
既定が「開いている」なので、この向きなら空配列が「すべて既定」を意味する。展開側を
保存すると、利用者が全部畳んだ状態と初期状態を区別できない。

checkout と FF マージは**項目としては出すが T-18 まで無効**にする。機能がどこにあるかだけ
先に示しておく。

**開閉の三角は文字ではなくボーダーで描く。** `▸` / `▾` は 10px では潰れて開閉が読めず、
2 つの字形を見比べる形になる（目視の指摘）。同じ三角を回転させれば、形は変わらず向きだけが
変わるので差が分かる。大きさをフォントに左右されないことも利点。

**ツリーとリポジトリ一覧の縦の取り合いは `flex-basis` で決まる。** ツリー側を `flex: 1 1 auto`
にすると、ref が数千本あるリポジトリ（vite / onyx）で中身の高さがそのまま基準サイズになり、
縮小が基準サイズの比で配分されて**リポジトリ一覧が 9px まで潰れた**（実測）。
スクロールするペインの基準は 0 にし、上段の「中身なり（最大 50%）」が先に決まるようにする。

**T-25（2026-09-06）で表は全部効くようになった。** 最後に残っていた `Ctrl+F` と
`Ctrl+,` をここで足している。
**T-18 でショートカットは増やしていない**（checkout とマージは確認を挟むので、

実装は `src/hooks/` に置く。**コミットの移動は `useCommitNavigation.ts`、

両方から呼ぶ。**見ているものが違うだけで操作は同じ**なので、2 つ書かない（T-16 で切り出した）。
どれも入力欄にフォーカスがあるときは横取りしない。

#### 6.5.1 T-25 で決めたこと（2026-09-06）

**キーの形は 1 か所（`src/lib/shortcuts.ts`）に集めた。ハンドラは統合していない。**
実装は 4 か所に散っている（`App.tsx` / `useCommitNavigation` / `useFileNavigation` /
`useWorkingTree`）が、**動いているものを全部書き直す**より、判定だけを
`matches(event, action)` に寄せるほうが安い。**設定画面の一覧も同じ表から作る**ので、
一覧と実際のキーがずれない（一覧が飾りにならない）。

**修飾キーは「書いていないものは押されていない」ことまで見る。** 緩く見ると
`Ctrl+Shift+R`（全 fetch）が `Ctrl+R`（現在のリポジトリ）にも当たる。
**同じ押し方が 2 つの動作に当たらないことはテストで固定してある。**

**`Esc` は入力欄でも効く。** 他のショートカットと扱いが違うのは、
ダイアログの中で打っている最中に閉じたいため（文字を打つ邪魔にならないキー）。
写しが 3 か所にあったので `hooks/useEscape.ts` へ寄せた。

**`Ctrl+F`（差分内検索）は「開いているファイルの差分の中だけ」**（利用者の判断）。
他のファイルやコミットはまたがない（またぐ検索は v1.1 の「コミット検索」）。

- **当たった行へ移動して囲む。文字そのものは塗らない。** 行の描画には既に
  語単位差分と構文色が載っていて、そこへ 3 つ目の色を重ねると
  **どれが変更でどれが検索結果か読めなくなる**
- 大文字小文字は区別しない（切り替えは v1 では持たない）
- **畳んである差分では開かない**（飛ぶ先が画面に無い）
- 判定は純関数（`src/lib/diffSearch.ts`）

## 7. 閲覧機能（v1 範囲）

### 7.1 v1 に含めるもの

1. ブランチ / タグ / リモート追跡ブランチの一覧
2. コミットログとグラフ
3. コミット詳細と親との差分
4. **任意の 2 コミット間の差分**
5. 任意リビジョンのファイルツリー閲覧とファイル全文表示

加えて checkout / fetch / FF マージ / clone（§8）。

### 7.2 差分表示

- **レイアウト**: side-by-side / unified 切替可（既定 side-by-side）
- **word-level ハイライト**あり
- **シンタックスハイライトは Shiki**。VS Code と同じ TextMate 文法で精度が最も高い。差分の
  可読性がこのアプリの価値の半分を占めるため、初期ロードの重さより精度を取る。言語別文法は遅延ロード
- **リネーム検出は `-M` のみ**。`-C`（コピー検出）はコストが高く誤検出も多いため使わない
- **空白無視トグル**（`-w`）と**コンテキスト行の増減ボタン**（既定 `-U3`）
- **1 ファイル 3000 行または 500KB 超は既定で折りたたみ**、明示操作で展開。
  素朴に DOM 化すると簡単に固まるため
- **バイナリ**は「バイナリファイル（サイズ変化）」の表示のみ。画像差分は v1.1

**パースは Rust 側に置く**（`git/diff.rs`。T-13 で骨子から変更）。改行コードは**内容行だけ**を
数える必要があり（§9.2）、ヘッダ行と内容行を分ける時点でパースそのものになる。
バイト列と文字コード判別を持っているのも Rust 側なので、二重に持つ理由がない。
フロントに残すのは**行の対応付けと語単位差分**で、どちらも純関数（`src/lib/diffView.ts`）。

**リネームでは pathspec に古いパスと新しいパスの両方を渡す。** 新しいパスだけを渡すと
git は対になる側が見えずリネームを検出できず、**全行が追加された新規ファイル**として出す
（実測。`tests/diff.rs` の `rename_needs_both_paths_in_the_pathspec` が固定している）。

**side-by-side は 1 行を 1 つの grid にする。** 行ごとに 4 列（旧行番号 / 旧本文 /
新行番号 / 新本文）を置くので、本文が折り返しても左右が同じ行に留まる。
列を縦に 4 本並べる作りだと、片側だけ折り返した瞬間に以降が全部ずれる。
**対応する行が無いところは空欄**にし、行番号も出さない。

**本文は折り返す**（横スクロールにしない）。左右で別々に横スクロールさせると行が見比べられず、
1 本にまとめると親ペインに 2 本目のスクロールバーが生える（CLAUDE.md §6）。

**語単位ハイライトは共通の先頭と末尾を削るだけ**にする。文字単位（コードポイント単位）で削り、
共通部分が長いほうの 30% 未満なら行全体を変更として扱う。LCS を回さないのは、日本語では
語境界が取れないうえ、実際の差分は「行内の 1 箇所を直した」が大半を占めるため。
まるごと書き換えた行に細かいハイライトを出すと、共通の記号（括弧やカンマ）が飛び飛びに
残ってかえって読めない。

**表示の切替は `settings.json` の `ui` に残す**（レイアウト / コンテキスト行 / 空白無視 /
改行の可視化）。毎回選び直したくないため。**文字コードの手動上書きだけは残さない** —
ファイルごとの判断なので、別のファイルへ持ち越すと黙って化ける。

**コンテキスト行は 0 / 3 / 10 / 25 / すべて**から選ぶ。「すべて」は十分大きな `-U` で代用する。

**ダークの差分色は輝度比を測って決めてある**（CLAUDE.md §6「明るさもライト / ダークで別に決める」）。
最初はペインの地 (`--bg-inset`) との比が 1.2 程度しかなく、**特に緑が青みの強い地に埋もれて
変更行を見分けられなかった**（目視で戻した）。取り直した実測値:

| | 行の地 ÷ ペインの地 | 語の強調 ÷ 行の地 | 本文 ÷ 語の強調 |
|---|---|---|---|
| 追加（緑） | 1.59 | 2.23 | 4.22 |
| 削除（赤） | 1.43 | 1.92 | 5.47 |

ライトは白地なので同じ値にはできない。**入れ替えるときは両方測り直すこと。**

**シンタックスハイライトは Shiki を遅延読み込みする**（T-14）。`shiki` のフルバンドルを
import すると全言語の文法が 1 チャンクに入るので、`shiki/core` に**言語ごとの動的 import**を
渡す。正規表現エンジンの wasm もローカル import なので、**外部 CDN へは出ない**
（CLAUDE.md §1）。拡張子 → 言語は表で持ち、**Shiki の別名に頼らない** — 別名があるのは
一部だけで、`mts` や `hpp` を渡すと「そんな言語は無い」で落ちる。表に無い拡張子は
ハイライトしない（総当たりで文法を読むより素の本文のほうが速く、外したときの色崩れもない）。

**トークン化は hunk の片側ごとにまとめて行う。** 行を 1 本ずつ渡すと、複数行にまたがる
文字列やコメントが行ごとに切れて色が壊れる。変更前（context + removed）と変更後
（context + added）をそれぞれ 1 本のテキストに戻して渡し、行へ配り直す。

**トークンと語単位差分は合成する**（`dangerouslySetInnerHTML` で Shiki の HTML を
流し込まない）。両者の区切りは互いに無関係なので、両方の境界で切り直したセグメント列を作る。
長さが食い違ったらハイライトを捨てる — **行がずれるくらいなら色が無いほうがまし**。

**語単位の強調の中では構文色を使わない。** 強調の地色は行の地より明るいので、
その上に構文色（github-dark は #0d1117 前提、github-light は #fff 前提）を載せると読めない。
実測:

| | 強調の中の文字 ÷ 強調の地 |
|---|---|
| 構文色を載せる（ダーク） | 1.97 〜 4.11 |
| 構文色を載せる（ライト） | 2.04 〜 2.42 |
| **本文の色 1 色（採用）** | **4.22 / 5.47（ダーク）、9.58 / 11.38（ライト）** |

強調を暗くして構文色を残す案も測った（ダークで文字 2.99〜、強調と行の地の比は 2.23 → 1.47）。
**両方の指標で下回る**ので採らない。変わった範囲で知りたいのは「何色のトークンか」ではなく
「どこが変わったか」である。トークンの境目で切られた強調は**続きになったものを 1 つに畳む**
（角丸の継ぎ目が見えるため）。

**差分本体は仮想スクロールする**（`@tanstack/react-virtual`。コミットリストと同じ）。
**hunk の見出しも同じ行リストに入れる** — 別に描くと見出しだけが仮想化から漏れ、hunk が
数千ある差分で結局全部 DOM に載る。**行の高さは実測する**（本文を折り返すので一定でない）。
推定値は 1 行ぶんでよく、折り返す行は少数なので総高さはほとんど動かない
（6000 行で実測後の伸びは 8px）。仮想化するとブラウザの `Ctrl+F` が可視部分しか
見つけられなくなるが、これは承知の上（コミットリストも同じ）。

**折りたたみ中は行の対応付けも語単位差分もトークン化も走らせない。** DOM を作らないだけでは
重さが消えない。規模の判定（行数と UTF-8 バイト数を数えるだけ）は安いので、それだけ先に行う。
**行数とバイト数のどちらか一方でも超えたら折りたたむ** — 行数だけ見ていると、1 行が極端に
長いファイル（minify 済みなど）を素通しさせる。閾値は `settings.json` の
`ui.collapseLines` / `ui.collapseBytes`（既定 3000 行 / 500KB）。展開は**ファイルごとの
一時状態**で、永続化も持ち越しもしない（文字コードの上書きと同じ理由）。
展開後の歯止めとして、**2 万行を超える差分はハイライトしない**（トークン化は同期処理なので、
桁違いの差分を渡すとその間だけ固まる）。

**バイナリはサイズの変化を出す。** `cat-file -s` ではなく `ls-tree -l` を使う —
無いパス（追加や削除の反対側）を `cat-file` に渡すと**失敗としてログに残る**が、
`ls-tree` は空を返して成功する。**片側が無いときは `None`。0 と書くと
「空のファイルになった」に読める。** この 2 回の追加実行は**バイナリのときだけ**行う。

**`ui.contextLines` を `u8` にしてはいけない**（T-14 で発見）。画面の「すべて」は
十分大きな `-U`（1000000）で代用しているので、`u8` だと設定の保存がまるごと弾かれる。

### 7.3 コミット詳細と変更ファイル一覧

**右の列**に 2 つを縦に積み、**差分本体は中央下**に置く（§6.1）。

1. **コミット詳細**（右上） — full message / 作者・コミッター / 親 / SHA
2. **変更ファイル一覧**（右下） — 既定はフラットなパス一覧（共通ディレクトリはグレーで薄く、
   ファイル名を強調）、ディレクトリツリーに切替可。ファイルごとに +N / -M と横バー、
   ヘッダに合計
3. **選択ファイルの差分**（中央下） — 見出しにパスと状態を出す。一覧が別の列にあるので、
   どのファイルを見ているかは差分側だけで分かる必要がある

ファイル間の移動は一覧クリック ＋ `Alt+↑` / `Alt+↓`。

**取得は 1 回で、右の列と差分本体が分け合う**（`useCommitFiles`）。2 つの枝に分かれたからと
いって 2 回取りに行かないこと。
**全ファイルを縦に連結してスクロールする方式は採らない**（大きな差分で確実に重くなる）。

**一覧は 1 回の git 実行で作る。** `diff --raw --numstat -z -M` は raw 区間と numstat 区間を
1 本の NUL 列に続けて出すので、状態（A/M/D/R）とファイルモードを raw から、増減行数と
バイナリ判定を numstat から取れる。2 回呼ぶ必要はない。**リネームだけ raw も numstat も
パスを 2 つ食う**ので、そこを数え違えると以降が全部 1 件ずつずれる。

**ルートコミットは `git diff` では出せない。** 親が無いので片側を指定できず、
`diff-tree --raw --numstat -z -M --root --no-commit-id -r <sha>` を使う。
API では親を `Option<String>` にし、`None` がルートを意味する
（空ツリーの SHA を定数で埋め込む手もあるが、SHA-256 リポジトリで値が変わる）。

**バイナリの増減は `null` であって 0 ではない。** numstat が `-` を返すので、
0 行の変更と区別できるようにしておく。合計にも足さず、「バイナリ N 件」として別に数える。

**ディレクトリツリーは子が 1 つだけの連なりを 1 行にまとめる**（`src/components/diff`）。
ref ツリー（§6.4）の「3 件以上で畳む」とは規則が違う — ファイルは実際のディレクトリ構造が
そのまま意味を持つので、1 件でもディレクトリはディレクトリとして出す。
**ディレクトリの開閉は持たない**（1 コミットの変更ファイルは高々数十件で、
畳む手間より全部見えているほうが速い）。

**フラット表示で削るのはディレクトリ側だけ**にして、ファイル名は必ず残す。
`direction: rtl` で末尾を残す手は、インライン要素の並びまで反転してディレクトリが
ファイル名の後ろに出る（T-11 の目視で確認）。

**リネーム元は行内に並べず 2 行目に置く。** 右の列は 380px 程度しかないので、
パスと増減を横に並べると押し合って両方読めなくなる。

### 7.4 マージコミットの差分

マージコミットは親が 2 つあるため「差分」が一意に決まらない。`git show` の既定はマージコミットに
対して何も出さない。

- **既定は第 1 親との差分**（`git diff <merge>^1 <merge>`）
- ヘッダに親を選ぶドロップダウンを出し、明示的に第 2 親も選べる
- `--cc`（combined diff）は v1.1

**ドロップダウンはコミット詳細の見出し行に置く**（作者・親を並べた欄ではない）。
本文が長いと欄までスクロールしなければ見えず、**どの親との差分を見ているか分からないまま
一覧を読むことになる**（T-11 の目視で確認）。

**親の subject は取り直さない。** 全コミットが手元にあるので（§4.1）一覧から引く。

**選んだ親は永続化しない。** 別のコミットへ移れば意味を失う値なので、`state.json` に
残すと「前に開いたマージの第 2 親」が無関係なコミットに適用されかねない。
コミットが変わったら第 1 親へ戻す。

### 7.5 作業ツリー

**read-only 表示のみ。** stage / discard / stash は一切提供しない。

- `git status --porcelain=v2 -z` で取得し、**ステージ済み / 未ステージ / 未追跡**の 3 セクションに
  分ける。CLI 派である以上、index と working tree の区別は当然見たいものとして扱う
- **未追跡ファイルは名前を列挙し、クリックで全文表示**（差分としては見せない。全行追加の差分は
  視覚的ノイズが大きすぎる）
- 実行タイミングは**リポジトリ選択時・ウィンドウフォーカス復帰時・`F5` のみ**。
  **ファイル監視は入れない**（ビルド中のプロジェクトで大量イベントが飛ぶ）
- **コミットリスト最上部に擬似行を 1 つ置く**。この行は**レーン計算の対象外**とし、HEAD のノードへ
  点線で接続する。作業ツリーがクリーンなときはこの行を出さない

**取得は git を 3 回**（T-16）。ステージ済みは `diff --cached --raw --numstat -z -M`、
未ステージは `diff --raw --numstat -z -M`、未追跡と衝突は `status --porcelain=v2 -z`。
前 2 つは**コミットの一覧と同じパーサをそのまま通せば**状態・モード・増減行数が揃うので、
`--porcelain=v2` は増減行数を持たない側の穴埋めにだけ使う。

**`--porcelain=v2 -z` はリネーム（`2` 記録）がパスを 2 つ食う。** 読み飛ばし方を間違えると
以降の記録が全部ずれ、元のパスが未追跡ファイルに見える。`u`（衝突）記録のパスは
**後ろから数えない** — 空白を含むパスがあるので、固定フィールドを 10 個飛ばして残り全部を取る。

**衝突しているパスは `diff --raw` にも出る**（状態 `U`。しかも未ステージ側には同じパスが
2 度出る）。衝突は別のセクションで数えているので、ステージ済み / 未ステージからは外す。
外さないと 1 つの衝突が 3 行に見える。

**セクションは 4 つ。** DESIGN の当初は 3 つ（ステージ済み / 未ステージ / 未追跡）だったが、
**衝突はそのどちらでもない**ので独立させ、**先頭に置く**（直さないと先へ進めない）。
空のセクションは見出しごと出さない。

**選択の鍵にセクションを含める。** `git add` したあとにもう一度直すと、同じパスが
ステージ済みと未ステージの両方に出る。パスだけでは前後が決まらない。

**擬似行はレーン計算の対象外**（CLAUDE.md §3-6）。グラフ側は**窓の置き場所だけ**を
1 行ぶん下げ、**viewBox は動かさない**。両方に足すと打ち消し合って、グラフが 1 行ぶん
上へずれる（実測で気付いた）。擬似行は自分でノードと点線を描く。
**点線を引くのは HEAD がすぐ下にあるときだけ** — 途中に別のコミットが挟まると、
線がどこへ向かっているのか分からなくなる。

**行の SVG は `display: block` にする。** 既定の inline だとベースラインの下に余白が付き、
ノードが行の中心から 4px 上へずれる（実測）。

**未追跡ファイルは git ではなくファイルを直接読む**（git はまだそのファイルを知らない）。
`encoding::decode` を通し、512KB を超えるものとバイナリは中身を返さない。
**`..` を含むパスは拒む** — 呼び出し元は自分が出した一覧を渡すはずだが、外へ出られる
経路は作らない。

**作業ツリーのバイナリにはサイズを出さない。** index と作業ツリーのバイト数は
`ls-tree` では引けず、片側だけ正しい数を出すと嘘になる。

**更新はリポジトリ選択時・ウィンドウフォーカス復帰時・`F5` のみ。** 外部の CLI で
`git add` した直後がまさにフォーカス復帰の瞬間なので、そこを外すと画面が古いまま残る。
**ファイル監視は入れない**（ビルド中に大量のイベントが飛ぶ）。

**「作業ツリーを見ている」状態は永続化しない。** 次に開いたときにはクリーンかもしれず、
そのときは擬似行ごと存在しない。

## 8. 書き込み系操作

### 8.1 checkout

- **起動点**: ブランチツリーの右クリックメニュー＋ダブルクリック、グラフの行の右クリック、
  **グラフの ref チップの右クリック**。チップと行は**別のメニュー**にする —
  ブランチ名の上で右クリックしたとき、「そのブランチへ切り替える」のか
  「そのコミットを detached で見る」のかは利用者にしか決められないので、両方出す
- **対象**: ローカルブランチ / リモート追跡ブランチ / タグ / 任意コミット。
  detached HEAD になる場合はダイアログで明示する
- **確認は必ず出す。** 押せない理由（bare / 汚れている / `index.lock` / コミット 0 件）も、
  detached になることも、そこへまとめて出す。**メニュー項目を無効にして説明を隠さない** —
  起動点が 4 つあるので、判定をメニューの側に置くと経路ごとに結論が食い違う
- **リモート追跡ブランチは、確認画面で選ばせる**（2026-09-04 に変更）。
  「ローカル追跡ブランチを作って切り替える」と「detached で開く」の 2 択を出し、
  **選ばれたときだけ `checkout -b <名前> --track <ref>` を実行する**

  当初は detached 固定にしていた。「git コマンドで実行するのは checkout / fetch / FF マージのみ」
  の厳格解釈で、ローカルブランチ作成は ref の新規作成だから範囲外、という理由である。
  実際に触ってみると**リモート追跡ブランチを開く目的の多くが「作業を続ける」ほう**で、
  そのたびにターミナルへ出る必要があった。利用者の判断で、
  **確認画面を挟むことを条件に**許すことにした。

  守っているのは「**黙って ref を作らない**」のほうで、そこは変えていない。
  作るのはこの 1 経路だけであり、`checkout -b` は同じ名前があれば失敗するので、
  既存のブランチを取り違えて上書きすることはない。同じ名前のローカルブランチが既にあれば、
  そもそも「作る」を出さず「そのブランチへ切り替える」を出す。
  **ブランチの削除・リネームとタグの操作は引き続き提供しない**

- **dirty なら事前に検出して中止**し、理由を明示する。`--force` と自動 stash は提供しない
  （ビューワーがユーザーの未保存作業を消す事故を構造的に不可能にする）

**checkout の対象は ref 名の形で渡し分ける**（2026-09-04 実測。T-18 の詳細化で確認）。

| 対象 | 渡し方 | そうしないと |
|---|---|---|
| ローカルブランチ | 短い名前（`main`） | 完全 ref 名だと git がブランチとして扱わず detached になる |
| リモート追跡 / タグ / コミット | 完全な ref 名 ＋ `--detach` | 短い名前だと**ローカル追跡ブランチが勝手に生える** |

短い名前だけを渡すと、ローカルに同名が無いとき git の DWIM（`checkout.guess` の既定が true）が
働き、`git checkout sideline` が `branch 'sideline' set up to track 'origin/sideline'` を出して
**ローカルブランチを 1 本作る**。これは ref の新規作成であり、宣言された制約に反する。

**短い名前に `--detach` を足して塞ぐことはできない。** DWIM が内部で `-b` を立てるため
`fatal: '--detach' cannot be used with '-b/-B/--orphan'` という、原因を指していないエラーで
落ちる。**完全な ref 名で渡すのが唯一の正しい塞ぎ方**であり、`--detach` はその上での念押し。

**detached HEAD から離れるときの警告は入れていない**（承知の上）。git 自身が警告し reflog に
残るうえ、**GitPeek はコミットを作れない**ので、この経路で失われる作業は
「利用者がターミナルで detached のままコミットした場合」に限られる。判定には ref 全部からの
到達可能性が要るので、必要になったときに入れる。

**未追跡ファイルだけなら checkout を止めない。** checkout は未追跡ファイルを消さず、
上書きになる場合は git 自身が拒む。ここで止めると、新しいファイルを書きかけの間は
ブランチを切り替えられなくなる。止めるのは staged / unstaged / unmerged があるときだけで、
未追跡の件数は確認ダイアログに出す（黙って通さない）。**`WorkingTree::is_clean()` は
未追跡も数える**ので、擬似行の判定とは別の述語にする。

### 8.2 FF マージ

- `git merge --ff-only` 固定
- 主動線は「現在のブランチに upstream (`@{u}`) を取り込む」
- 加えて任意 ref の右クリックから「現在のブランチに FF マージ」も可
- FF 不可なら実行せず理由を表示するだけ

**可否は手元のグラフから数える**（`ahead == 0 && behind > 0`）。`git merge-base --is-ancestor`
は呼ばない（§4.5 と同じ理由）。**可視 ref で絞る前の全コミット集合で判定する** —
表示を絞ってもグラフから消えるだけで、履歴は変わらない。

**判定しても `--ff-only` は外さない。** 判定と実行の間にリポジトリは動きうるので、
そこは git に止めてもらう。二重に見えるが、外すと「判定が古かったとき」に
非 fast-forward マージが通ってしまう。

**メニュー項目は常に押せる。** 押せない理由（進んでいる / 取り込むものが無い /
detached / 判定できない）は確認画面に出す。無効なメニュー項目とツールチップより、
ダイアログ 1 枚のほうが読まれる。

### 8.3 fetch

- `git fetch --all --prune --tags` 固定（ここでの `--all` は「全リモート」の意味で、§4.2 の
  `git log --all` とは別物）
- **手動のみ。定期自動 fetch は持たない。**

  自動 fetch には具体的な危険がある。認証キャッシュが切れているリモートに対して自動 fetch が
  走ると、ユーザーが何もしていないのに GCM の認証ウィンドウが突然前面に出る

- 現在のリポジトリ / 全リポジトリ一括の両方のボタンを用意
- **一括 fetch は実行前に確認ダイアログを 1 回**（対象数＋認証ウィンドウが出る可能性を明示）。
  実行中は進捗表示とキャンセル可、完了後にリポジトリごとの成功 / 失敗サマリ
- **放置警告は `.git/FETCH_HEAD` の mtime で判定する。**

  アプリ独自に記録すると、ターミナルで `git fetch` した直後にアプリが「10 日 fetch していません」と
  誤警告する。`FETCH_HEAD` の mtime なら CLI 併用でも整合が取れる。ファイルが無い＝一度も fetch
  していない、として扱う

- 閾値は既定 7 日、設定で変更可、0 で無効化
- 表示は**リポジトリ一覧行の控えめなアイコン＋ツールチップのみ**。モーダルもバナーも出さない

#### 8.3.1 T-17 で決めたこと

**進捗は stderr から読む。** git の `--progress` は stdout ではなく stderr に出す。
既存の `exec::run_streaming` は stdout を読みながら返し stderr は別スレッドで読み切る
形なので、そのままでは進捗が全部終わってから 1 度に届く。**stderr を読みながら返す
入口 `exec::run_progress` を足した**（固定オプションは `build()` を通るまま）。

**`\r` と `\n` の両方で行に切る。** git は `\r` で同じ行を上書きしていくので、
`\n` だけで切ると 1 行も確定しないまま最後にまとめて届く。バーが一度も動かない
症状はこれ。断片は UTF-8 の途中で切れうるので、**バイトのまま溜めて行単位で復号する**。

**進捗のラベルで判定しない。** git は環境によって進捗そのものを翻訳する
（`Receiving objects` が「オブジェクトを受信中」になる）。`(済/全)` と `%` だけを
構造で取り、ラベルは読み取らずそのまま表示へ回す。

**`--prune-tags` を足さない。** `--prune --tags` はタグを消さない。足すとローカルに
しか無いタグが消え、**ref の削除**になる（CLAUDE.md §1 違反）。

**リモートが 1 つも無いリポジトリでは放置警告を出さない。** fetch しても
`FETCH_HEAD` はできないので、出すとローカルだけのリポジトリで永久に出続ける。
`RepositoryProbe` に `remotes` を足して判断する。

**放置判定は Rust 側の 1 箇所（`git::ops::is_stale`）だけ。** `list_repositories` が
設定の閾値と合わせて `RepositoryEntry.fetch_stale` を計算する。フロントで日数を
数え直すと「リモートが無ければ出さない」「閾値 0 で無効」が二重管理になる。
未来の mtime（時計のずれ）は「古い」と扱わない。

**中止は失敗ではない。** 中止すると git は非ゼロで落ちるので、成否を先に見ると
利用者自身の操作を「失敗しました」と報告することになる。**中止の判定を先に置く。**
そして**中止しても、そこまでに更新された ref は戻らない**ので、結果にそう書く。

**キャンセルは旗を見張る別スレッドから子プロセスを落とす。** 読み取りは呼び出し元を
塞ぐので、認証待ちのように何も出ないまま止まる場面では読み取りの合間の判定が効かない。
`wait()` は lock を握ったまま待つので、**見張りは `wait()` より先に畳む**（さもないと
二者が待ち合って固まる）。落とせるのは起動した git 本体だけで、その子は追って終わる。

**一括はフロントが 1 件ずつ呼ぶ。** 並列にすると認証ウィンドウが同時に何枚も開く。
確認ダイアログは**一括のときだけ 1 回**。1 件の fetch には出さない。

**進捗バーの「約」は呼び出し側が決める。** 履歴の読み込みは前回件数を分母にしている
ので「約」が要るが、fetch のオブジェクト数は git が数えた正確な値なので、
「約」を付けると逆に嘘になる（`LoadProgress` の `estimated`）。

**`Ctrl+R` は WebView のページ再読込に取られる。** 必ず `preventDefault` する。

**上流がタグを付け替えたときは「一部成功」にする。** git は `--force` 無しでは同名の
タグを上書きしないので、`! [rejected] v4.6.6 -> v4.6.6 (would clobber existing tag)` を
出して非ゼロで終わる。**ブランチは取り込めている**ので、これを「失敗しました」で
片付けると、直しようがないのに壊れたように見える。`FetchStatus::Partial` を分け、
弾かれたタグ名と `git fetch --tags --force`（**利用者がターミナルで実行する**）を伝える。
**アプリはタグを書き換えない**（CLAUDE.md §1）。

**primary ボタンの hover は accent 系で持つ。** 共通の `.button:hover` は中立の
`--bg-hover` を当てるので、primary に効かせると文字（`--accent-contrast`）との輝度比が
**ライト 4.57 → 1.20 / ダーク 6.95 → 1.30** まで落ち、文字が地に溶けて「押せない」ように
見える。`--accent-hover` を別に持ち、ライト 5.67 / ダーク 8.54 を確保した（ページ上で実測）。

**ダイアログの中のボタンは折り返す。** 共通の `.button` は `white-space: nowrap`
（狭いペインでラベルを割らないため）だが、**ラベルにブランチ名が入る**場所でそのままにすると、
長い名前でボタンが箱の外へ出る（実測: ボタン 507px / 箱 480px、左へ 52px はみ出す）。
`.modal__actions .button` で `white-space: normal` ＋ `overflow-wrap: anywhere` に戻す。

### 8.4 clone

- 既定ワークスペースルートを設定に持ち、`<root>/<name>` を埋めたダイアログを毎回出して確認させる
- HTTPS を主に据えつつ、SSH URL も git に素通しする
- **shallow とブランチ指定は提供しない**（履歴グラフが目的なので shallow は本末転倒）
- **submodule 再帰は確認画面のチェックボックスで選べる**（2026-09-05 に追加。既定 OFF — 下記）
- `--progress` の stderr をパースして実バー表示
- 失敗時は確認ダイアログの上で残骸ディレクトリを削除

**保存先は「親フォルダ」と「フォルダ名」に分けて受け渡す**（T-19）。区切り文字を繋ぐのは
Rust 側 1 か所だけにしてある。画面が出すパスはプレビューであり、**実際に作られた場所の正は
`CloneOutcome.path`**。登録（`add_repository`）にはそちらを使う。

**フォルダ名を決められないときは空にして、利用者に入力させる**（`src/lib/clonePath.ts`）。
`https://github.com` のようにリポジトリを指していない入力から適当な名前を作ると、
気付かないまま見当違いの場所へ数百 MB が落ちる。なお **SCP 形式（`git@host:owner/repo.git`）は
URL としてパースできない**ので、`new URL()` に通す実装にしてはいけない（`:` が区切りになる）。

**既にあるフォルダには clone しない。** git も拒むが、**その前に自分で見て自分の言葉で言う**
（`fatal: destination path 'x' already exists and is not an empty directory.` より読みやすい）。
実行前に見ることには、もう 1 つの役目がある — 下記の後始末の前提になる。

#### 確認画面で選べるもの（2026-09-05 に利用者の判断で追加）

clone の入力欄の下にチェックボックスを 2 つ置いた。**どちらも既定 OFF**で、
**ラベルの下に「何が起きるか」を 1 行添える**（T-18 の「FF マージ」と同じ失敗をしないため）。

| 選択肢 | 効果 | 既定 |
|---|---|---|
| サブモジュールも取り込む | `--recurse-submodules` を足す | OFF |
| この保存先を次回から既定にする | `settings.json` の `workspaceRoot` を書き換える | OFF |

**サブモジュールは §1.1 の非対象から外した**（CLAUDE.md §1 も書き換え済み）。ただし外したのは
「利用者が明示的にチェックしたとき」だけで、**黙って取り込まないことが守るべき側**。
リモート追跡ブランチからローカルブランチを作る件（§8.1）と同じ形の緩和である。
**`--shallow-submodules` は付けない** — サブモジュールだけ履歴が欠けると、そのフォルダを
別途「追加」で登録しても読めない。§1.1 の shallow を禁じた理由がそのまま当てはまる。

**サブモジュールを取り込むと進捗が何度も 0 に戻る。** git はサブモジュールごとに
`Cloning into '<path>'...` から数え直すためで、`fetchprogress.rs` はラベルを読まず
`(済/全)` と `%` だけを構造で取るので**パーサはそのまま通る**。ただし画面では
「止まった／やり直している」と読まれうるので、実行中にその旨を 1 行出す。

**サブモジュールが実際に取り込まれることは結合テストで確かめられない。** git 2.38 以降は
サブモジュールの `file` トランスポートを既定で拒む（`fatal: transport 'file' not allowed`。
この環境の git 2.43 で実測）ので、生成したローカルの上流では成功しない。
`protocol.file.allow` を緩めるのは**全 git 呼び出しに効いてしまう**ため行わない（CLAUDE.md §2）。
代わりに **`--recurse-submodules` が実際に起動したプロセスの引数へ届いていること**を
コマンドログで固定してある（`tests/clone.rs` の `the_submodule_flag_reaches_git`）。
実物での確認は目視に回す。

**「この保存先を次回から既定にする」は成功したときだけ保存する。** 失敗した場所を既定に
すると、同じ失敗を繰り返す入口になる。**T-25 で設定画面からも変えられるようになった**が、
clone の流れの中で決められることに意味があるので、こちらは残してある。

**押せないときもチェックボックスを消さない**（目視で報告されて直した）。最初は「既定と同じ
場所なら意味が無いので出さない」としたが、**保存先の欄は既定で初期化される**ので条件が
常に成立し、一度 `workspaceRoot` を決めたあとは二度と現れなくなった。既定がどこにあるのかも
画面から読めないため、**勝手に変わっているようにしか見えない**。押せない状態で残し、
**どの状態でもいまの既定を文言に出す**。

**パスの比較は Rust 側 (`store/mod.rs` の `same_path`) と揃える。** 末尾の区切りと大文字小文字
だけが違うものを「別の場所」と読むと、既定が `C:\Gitwork` と `C:\Gitwork\` の間で往復する。

**この判定は純関数に置く**（`src/lib/clonePath.ts` の `rememberOption`）。コンポーネントに
直書きしていたのが、テストが 1 つも当たらなかった理由である（CLAUDE.md §8 —
フロントは純関数だけテストする）。

**`--filter=blob:none`（partial clone）は入れない。** 履歴グラフは完全なまま速くなるので
shallow とは別物だが、**差分を開くたびにネットワークへ出る**ことになり、差分を読むのが
主目的のビューワーとしては筋が悪い（オフラインで差分が開けなくなる）。

#### 中止したら残骸を消す（fetch と扱いが違う）

fetch は「中止しても、そこまでに取り込まれた ref は戻らない」と伝えて残す（§8.3）。
clone は逆に**消す**。途中まで取り込まれたフォルダは開けるリポジトリになっておらず、
残しても利用者が手で消すだけだからである。失敗時も同じ。

**消してよいのは自分が作ったフォルダだけ。** 実行の直前に `symlink_metadata` で
「無かった」ことを確かめられたときにしか消さない。確かめられなかった場合（権限など）は
**消さずに場所を伝える**。利用者の既存フォルダを消す事故を、条件分岐ではなく
「消してよいと分かっているときだけ消す」という構造で潰してある。

#### Job Object は入れない（T-19 で決着）

`exec::run_progress` が落とせるのは**起動した git 本体だけ**で、`git-remote-https` のような
子プロセスは残りうる（§8.3 の割り切り）。clone は fetch より長く走るので T-19 で決着を
付けることにしていた。**入れない**を選んだ。理由は 2 つ。

1. **プロセスツリーごと落とすには Windows の Job Object が要り、`windows` crate への直接依存が
   増える。** 得られるのは「子も即座に落ちる」ことだけで、**利用者から見える違いは
   残骸フォルダを消せるかどうかに集約される**
2. その残骸は**再試行で消せる**。中止直後に消せないのは、子がまだ pack の一時ファイルを
   掴んでいる短い間だけで（Windows は掴まれたファイルを消せない）、親が死ねば子も追って
   終わる。`clean_up` は 100ms × 20 回（最大 2 秒）まで `remove_dir_all` を試す

2 秒待っても消せなければ、**消せなかったことと場所を結果に出す**。黙って残さない。

#### 秘匿情報

**URL 欄には `https://<user>:<token>@…` が貼られうる。** 引数はそのまま `git clone` へ渡るので、
**コマンドログが平文の入口になる**。`commandlog.rs` の `redacted()` が `args` を通しているため
ログ側は塞がっているが、結果の `message` / `lines` も `redact.rs` を通すこと（CLAUDE.md §4）。
`tests/clone.rs` の `credentials_in_the_url_are_masked_everywhere` が両方を固定している。

### 8.5 書き込み後の再読込

書き込み操作の実行後は**全コミットメタ情報を再取得してレーン再計算**する。
数万コミットで 1 秒未満なので、部分更新の複雑さを持ち込まない。

**checkout のあとは HEAD へ寄せる。** HEAD が動いても選択行はそのままなので、
少し古いブランチへ切り替えると**選択が数百行下に取り残され、自分の居場所を見失う**
（T-18 の目視で指摘された）。読み直しが終わってから移動すること — 先に呼ぶと
まだ古い HEAD を指している。`Ctrl+H` を知らなくても戻れるよう、
コミットリストのツールバーにも「HEAD へ」を置く。

## 9. 文字コード・改行・ファイル属性

閲覧対象に Linux 由来のソースが含まれる以上、ここは事故が起きる場所である。

### 9.1 文字コード

**自動判別。** UTF-8 として妥当なら UTF-8、失敗したら Shift_JIS → EUC-JP の順で試行する。
判別結果をファイルごとにステータス表示し、手動で上書き可能にする。
実装は `src-tauri/src/encoding.rs`（T-12）。

**バイナリ判定を先に行う。** 先頭 8000 バイトに NUL があればバイナリとし、デコードしない。
**範囲を git と同じにしてある** — 広げると、git が差分を出したファイルをこちらだけが
バイナリ扱いする食い違いが起きる。BOM 付き UTF-16 もここでバイナリになる（git も同じ）。

**試行は置換なしの厳密デコード**で行い、どれも通らなければ **UTF-8 の置換ありデコード**に
落として `lossy` を立てる。ASCII 部分は読めるので、この環境では最も傷が浅い。
**UTF-8 BOM は取り除いてから**判別する（残すと差分の先頭に U+FEFF が出る）。

**この方式の限界を承知で採っている。** EUC-JP のひらがなは 1 バイトずつが Shift_JIS の
半角カナとして妥当なので、**厳密デコードが通ってしまい Shift_JIS と判定される**
（`encoding.rs` の `euc_jp_hiragana_is_misdetected_as_shift_jis` が固定している）。
置換文字も出ないので、**画面に化けた半角カナが並ぶまで気付けない**。

- 直す手段は**手動上書き**である。だから上書き API を最初から持たせてある
- 統計的推定（`chardetng` 等）は v1 では入れない。判別の当たり外れが入力次第になり、
  「なぜこのファイルだけ違う結果か」を説明できなくなる。**順序なら常に説明できる**
- EUC-JP のリポジトリを常用することになったら v1.1 で再検討する

### 9.2 改行コード

- 改行コード（LF / CRLF / CR）を**ステータスバーに常時表示**
- 可視化記号はトグル（既定オフ）
- **1 ファイル内で混在したら警告アイコン**

  Linux 用シェルスクリプトに CRLF が混入すると実行時に壊れるため、目視で気づけることに実利がある

**CRLF を CR と LF に二重計上しない。** 数え方を間違えると全ファイルが「混在」になり、
警告が意味を失う。

**数え上げは渡したバイト列そのものに対して行う。** 何を渡すかは呼び出し側が決める。
**diff 出力をまるごと渡してはいけない** — ヘッダ行（`@@` や `+++`）は常に LF なので、
CRLF のファイルが全部「混在」と出る。**内容行だけを渡すこと。**

**可視化記号はサクラエディタに合わせる**（CRLF は `→↓`、LF は `↓`、CR は `→`）。
`␍␊` のような制御文字の記号は、並べてもどちらがどちらか読み取れない。
**末尾に改行が無いことだけは記号ではなく「改行なし」と書く** — 「無い」ことを表す記号は伝わらない。
こちらは可視化トグルに関わらず常に出す（差分の意味が変わるため）。

### 9.3 ファイル属性

- ファイルモード変更（`100644` → `100755`）を差分ヘッダに明示
- シンボリックリンクは「シンボリックリンク → 参照先」として明示

**どちらも `FileChange` の `oldMode` / `newMode` から出す**（`120000` がシンボリックリンク）。
差分ヘッダのために git を呼び直さない。リンク先は差分の本文にそのまま出る
（シンボリックリンクの中身はリンク先のパス 1 行）。

## 10. AI レビュー

### 10.1 プロバイダ

**OpenAI 互換 API 1 系統に統一する。** Ollama も `http://localhost:11434/v1` で受けられるため、
ネイティブ API (`/api/chat`) の別実装は持たない。`/v1/models` を叩いてモデル名を補完する。

### 10.2 プロファイル

複数保存し、レビュー実行時にドロップダウンで選択する。リポジトリごとに既定プロファイルを記憶する。

保持項目: 名前 / base URL / モデル / コンテキスト長 / temperature / max tokens。

**API キーは Windows 資格情報マネージャーに保存し、設定 JSON には参照キーのみを書く。**
設定ファイルに平文の API キーを置かない。

#### 10.2.1 T-20 で決めたこと（2026-09-05）

**依存を 2 つ足した。利用者の判断で最新版を採った。**

| 何を | 選んだもの | 理由 |
|---|---|---|
| 資格情報 | `keyring 4.2`（既定機能 `v1`）| `CredWriteW` を直に叩くと**このプロジェクト初の `unsafe`** とワイド文字列の自前変換が要る。依存 1 つと引き換えに unsafe ゼロを保つ。既定機能で `Entry::new(service, user)` がそのまま使え、ストアの登録は初回アクセス時に自動で走る。プラットフォーム別のストアは `Cargo.toml` の target で絞られるので、Windows では `windows-native-keyring-store` だけが入る。**MSRV が 1.88 へ上がる**（§2.5）|
| HTTP | `ureq 3.4`（既定の rustls）| このコードベースは全部ブロッキング ＋ `spawn_blocking`（`git/exec.rs`）。T-22 の SSE も `run_progress` と同じ「チャンクを読んで行に切る」形でそのまま書ける。`reqwest` を入れると async の流儀が 2 つ並ぶ |
| モックサーバ | `std::net::TcpListener` で自作 | dev-dependency を増やさない。必要なのは固定レスポンスを返して要求を記録するだけ |

**キーの平文が通る経路は 2 本しか無い。**

1. 画面 → `save_llm_profile` → `secret::Secrets` → 資格情報マネージャー
2. `secret::Secrets` → `llm::client` → `Authorization` ヘッダ

とくに **2 本目をこの形にするために、通信は「保存済みのプロファイル」だけに許す**
（`test_llm_connection` / `list_llm_models` はプロファイル ID しか受け取らず、キーは Rust 側が
資格情報マネージャーから読む）。フロントから平文のキーを受け取って試せるようにすると、
保存していないキーが通る 3 本目の経路ができる。その代わり、**押せない理由を画面に出す**
（「先に保存すると試せます」。`lib/llmProfile.ts` の `probeOption`）。

**外へ出る文字列は `client.rs` の `sanitize` を通す。** `redact.rs` の規則に加えて、
**いま使ったキーそのもの**を伏せる。自前サーバの任意文字列のような、規則に当たらない形の
キーでも結果に現れないことをこれで担保している。

ただし**伏せるのは「独立した語」として現れたときだけ**（`mask_key`）。素の `replace` にして
いたところ、**1 文字のキー（`a`）で 401 の応答が壊れた**（2026-09-05 の目視）——
`message` が `mess***ge` になり、JSON のキー名まで潰れて `server_message` が理由を取り出せず、
見出しから「接続先の言い分」が消えた。前後が ASCII 英数字なら別の語の一部と見なして触らない。
`_` と `-` は区切り扱いのままにしてある（`prefix_<key>` は伏せたい）。伏せたいのは
`Bearer <key>` や `"api_key": "<key>"` のように区切りに挟まれた形であって、偶然の部分一致ではない。

**参照キー（`credential_key`）は `llm/<uuid>` を採番し、以後変えない。** 名前や base URL を
変えても資格情報を追いかけ直さなくて済む。**採番と据え置きを決めるのは `Store::upsert_llm_profile`
だけ**で、フロントから届いた値は使わない — 参照キーを呼び出し側に選ばせると、別のプロファイルの
資格情報を指す形が作れてしまう。**プロファイルを消したら資格情報も消す**（孤児を残さない）。

**API キー欄は「空欄＝変えない」。** 空欄を「消す」にすると、名前だけ直して保存したときに
キーが消える。消すのは明示的に選んだときだけで、この 3 通りを**真偽値ではなく種類**で送る
（`ApiKeyUpdate` の `keep` / `replace` / `clear`）。

**失敗は「見出し ＋ 接続先の言い分 ＋ 展開で生の応答」の 3 段。** 目視でエラーの原因が
読めないという指摘が出たため（2026-09-05）、ステータスから作る見出しに**サーバ自身の説明**を
1 行足した（`server_message`）。OpenAI (`error.message`) / Ollama (`error`) / プロキシ (`message`) /
FastAPI 系 (`detail`) の 4 つを順に見て、読めなければ黙って諦める。**見出しは 1 行に潰して
200 文字で切る** — 数十行のスタックトレースを見出しに入れない。抽出元の本文は `sanitize` を
通ったあとのものなので、ここでキーが混ざる余地は無い。

生の応答は**フロントで整形する**（`lib/llmMessage.ts`）。JSON として読めたときだけ字下げを付け、
読めなければ触らない（HTML のエラーページを JSON のつもりで加工すると原因が消える）。
Rust 側が切った応答は壊れているので `text` 側へ落ちる — **整形できたふりをしない。**

**接続テストは `/v1/models` で済ませない。** Ollama は認証不要なので models が通っても生成まで
通るとは限らない。`POST /chat/completions` に `max_tokens` 小さめで 1 往復させ、応答が返ることまで見る。
**タイムアウトは接続 10 秒 / 応答 120 秒**（ローカル Ollama は初回のモデルロードで数十秒かかる。
短くすると「壊れている」ように見える）。

### 10.3 起動と比較の意味

- **主動線は「2 つのコミットを選んでレビュー」**。グラフ上で Ctrl+クリックの 2 点選択
- 比較は**既定 `git diff A B`**（2 点間のツリー差分。「コミット間の差分」の素直な解釈）、
  トグルで `git diff A...B`（マージベース起点）に切替可
- ブランチ同士の比較は v1.1
- **fetch 後の自動レビューは v1 では持たない**（コストとレイテンシがユーザー不在で発生するため）
- 作業ツリー差分もレビュー対象にできる

**2 点比較は差分ペインをそのまま使う**（T-15）。`changed_files` も `file_diff` も
「親と比べる」ではなく**「2 つのリビジョンを比べる」**形になっているので、比較元を
`parent` に渡すだけでよい。専用のビューは作らない。

**`A...B` は 1 つの引数として渡す。** `A` と `B` を別々の引数で渡すと、git は
ただの 2 点間差分（`A B`）として扱う。マージベース起点にならないので黙って結果が変わる。

**共通の祖先が無い 2 点では `A...B` が失敗する**（git は `no merge base` としか言わない）。
これだけは Rust 側で言い換える — 何を選んだせいで失敗したのかが分からないため。
`A B` は成立するので、無関係な履歴どうしでもツリーの差は見られる。

**取得側は「1 点か 2 点比較か」を `DiffScope` で受ける**（`useCommitFiles`）。
違いは 2 つだけ: **比較では親を自分で決めない**のと、**コミット詳細を取りに行かない**
（`show -s` は 1 点のためのもの）。差分本体は一覧を作ったときの 2 点（`DiffRange`）を
そのまま使う。詳細から組み直すと、読み込み中に一覧と差分が別の組を見ることがある。

**`Ctrl+クリック`（Mac は `Cmd`）で比較を始める。** 「**今の選択を比較元へ押し出して、
押した先を比較先にする**」という向きにしてある。`A` を選んでから `B` を `Ctrl+クリック`
すれば「A から B への差分」になる。**比較中は比較元を動かさない**（起点を固定したまま
比較先だけ付け替えられる）。普通のクリックは比較を解除する — 比較したまま 3 点目を
選べる意味は無い。**自分自身との比較にはしない**（差分が空になるだけで、比較の見た目
だけが残る）。遷移は純関数（`src/lib/compareSelection.ts`）でテストする。

**比較元の行は塗りではなく左端の帯で示す。** 選択と同じ塗りにするとどちらが起点か
分からず、まったく別の塗りにすると 2 行が無関係に見える。

**比較元は `state.json` に残し、`A...B` かどうかは残さない。** どのコミットを見ていたかは
再訪時に効くが、比べ方は**その比較かぎりの判断**なので持ち越すと意図しない結果が出る。

### 10.4 実行前パネル（必須）

- 対象ファイル一覧＋個別除外チェック
- skill の複数選択
- LLM プロファイル選択
- **概算トークン数**（文字数 ÷ 4 の粗い見積で足りる）
- コンテキスト長を超えるファイルには「hunk 分割されます」バッジ

### 10.5 投入単位

**ファイル単位で個別レビューし、最後に全体サマリを生成する。**
1 ファイルが設定トークン上限を超える場合のみ、自動で hunk 分割にフォールバックする。

差分全体を 1 リクエストにするとローカル Ollama のコンテキスト長（8k〜32k）を容易に溢れる。
逆に hunk 単位を既定にすると文脈が細切れになりレビュー品質が落ちる。

モデルに渡すのは **ファイルパス ＋ unified diff（`-U10`）＋ コミットメッセージ ＋ skill 本文**のみ。
**ファイル全文は渡さない**（トークン効率が悪すぎる）。リポジトリ構成情報も v1 では渡さない。

### 10.6 出力形式 — JSON 要求 + Markdown フォールバック

**JSON スキーマを要求し、パースできればインライン指摘＋サマリ表示。失敗したら生出力を Markdown
として表示して「構造化に失敗しました」を添える。**

構造化 JSON だけを前提にすると、ローカルの小型モデル（7B 級）がスキーマを守れなかったときに
レビューが丸ごと失われる。フォールバックはこれを防ぐための必須経路である（テストでも必ず通す）。

要求する JSON スキーマ:

```json
{
  "summary": "このファイルの変更に対する要約",
  "findings": [
    {
      "file": "src/foo.ts",
      "line": 42,
      "severity": "critical | major | minor | info",
      "title": "短い見出し",
      "message": "詳細な指摘"
    }
  ]
}
```

出力言語は skill 側で指定する。内蔵 skill は日本語出力。ストリーミング表示あり
（ローカル Ollama は遅いので体感差が大きい）。

### 10.7 実行制御

- **既定は逐次（並列度 1）、設定で最大 3 まで**。ローカル Ollama は並列リクエストで総スループットが
  むしろ落ちることが多い
- いつでもキャンセル可能
- **1 ファイルの失敗では全体を止めない。** ファイル単位でエラーを記録し、サマリに「N 件失敗」を明示

#### 10.7.1 T-22 で決めたこと（2026-09-05）

**新しい依存は足していない。** SSE は「チャンクを行に切って `data:` を読む」だけで、
`git/fetchprogress.rs` の `LineSplitter`（`\r` でも `\n` でも切る／UTF-8 の途中で切れた
断片をバイトのまま溜める）がそのまま使える。並列度は最大 3 なので `std::thread::scope` で足りる。

**差分本文は `FileDiff` の hunks から組み立てる**（`llm/review.rs` の `unified_text`）。
`git diff` の生出力を別経路で取り直さないのは、`git/diff.rs` の `file_diff` が
**文字コードの判別を済ませてある**ため — 生の stdout を載せると **Shift_JIS のファイルで
JSON が壊れる**。組み立てが純関数になった結果、**hunk 分割が「渡す hunk を選ぶだけ」**になった。

**トークン見積もりは Rust 側だけに置く**（`文字数 ÷ 4`。§10.4）。実行前パネルの概算と
hunk 分割の判定が**同じ数**でなければならず、TS と Rust に 1 つずつ置くと必ずずれる。
フロントへは計算済みの数と「分割されます」の印（`parts >= 2`）を渡す。
`文字数 ÷ 4` は日本語で大きく外れる（1 文字 ≒ 1 トークン）が、**外したときは
接続先の超過エラーで拾う**ので、見積もりを賢くする代わりに拾う経路を置いた。

**`response_format: {"type":"json_object"}` は送る。** 当初は「OpenAI 以外は 400 で落ちる」
と考えて送らない案にしていたが、2026-09-05 に利用者の指摘で撤回した —
**Ollama は OpenAI 互換層でこれを `format: "json"` に読み替える**ので落ちないし、
**§10.6 がフォールバックを必須にした理由（小型モデルがスキーマを守れない）に一番効く指定**
だった。ただし受け付けないサーバに当たると全ファイルが 400 で落ちてレビューが丸ごと
失われるので、**咎められたら外して 1 度だけ投げ直す**。`format: json` だけでは空白を
吐き続けることがあるので、**プロンプトでの JSON 要求は外さない。**

**400 の扱いは 3 系統**で、振り分けは `llm/client.rs` の `retry_hint` に置く
（`server_message` の解釈を外へ持ち出さない）。

| 接続先の言い分 | すること |
|---|---|
| `response_format` を咎めている | 外して 1 度だけ投げ直し、**以後その実行では付けない** |
| 文脈長・トークン数を咎めている | 分割して投げ直す |
| どちらでもない | **投げ直さない。** そのファイルだけ失敗として記録して次へ進む |

**ストリームのマスクは末尾を持ち越してから流す**（`client.rs` の `Masker`）。
チャンクの切れ目で秘匿情報が割れると、チャンクごとに `sanitize` を掛けても素通りする
（T-20 で踏んだ「1 文字のキー」と同じ種類の穴）。溜めた全文にマスクを掛け直し、
**末尾 64 文字を除いた分だけ**流す。マスクで縮むのは必ず末尾側（＝まだ流していない範囲）
なので、流した分は動かない。

**幅は体感に直結する。** 当初 256 文字にしていたところ、**それより短い応答では
差分が 1 度も流れず、最後にまとめて 1 回だけ届いていた**（2026-09-06 の目視で
「少しずつ流れない」として上がった。ローカルの短いレビュー結果はほぼこれに当たる）。
64 文字は `redact` が見るトークンの形（`sk-` ＋ 40 字程度、`ghp_` ＋ 36 字）が丸ごと
収まり、かつ数語ぶんの遅れで済む幅。**鍵そのものがこれより長いときは鍵の長さまで広げる**
——固定幅のままだと、長い鍵がチャンクにまたがったときに繋がる前に流れる。

**残る割り切りは、64 文字より長い秘匿情報が実行中の画面に一瞬出うること。**
保存される結果と最終の本文は全文にマスクを掛け直したものなので、そちらには出ない。

**ストリーミングの待ち時間は別立て**にした。`timeout_global` 120 秒のままだと
**長い生成を途中で切ってしまう**ので、接続 10 秒 / 最初の応答まで 120 秒 /
本文を読み終えるまで 600 秒とする。無制限にしないのは、黙り込んだサーバから永久に
返らない経路を作らないため。

**「使う」と決めた skill が 1 つも当てはまらないファイルはレビューしない。**
観点無しで投げるとモデルが勝手な基準で書く。**除外して理由を出す**ほうが読める
（実行前パネルの `skipped`）。同じ理由で、**使う skill が 0 件なら実行そのものを止める**
（`ReviewPlan.blocked` に理由を入れて画面へ出す）。

**コミットメッセージを渡すのは「1 つのコミットとその親」を見ているときだけ。**
`DiffSource::Range { parent: Some(a), sha: b }` は「コミット `b` を親 `a` と比べている」と
「無関係な 2 点を比べている」の**どちらでも同じ形**なので、**実際に親子かどうかを
git に聞く**（`diff::is_parent_of`）。2 点比較（`A...B` 含む）と作業ツリーでは渡さない —
何のメッセージなのか決まらないものを、決まったふりで渡さない。

**中止したときと 1 件も読めなかったときは全体サマリを作らない。** 途中までの結果から
全体を語らせないため、および**要約する中身が無いのに 1 往復させない**ため
（全ファイルが 400 で落ちる接続先で、無駄に 1 回多く踏みに行くことになる）。

**`DiffSource` を `lib.rs` から `git/diff.rs` へ引っ越して差分ペインと共用した。**
レビューも差分も同じものを指すので、型を 2 つ持つとワイヤ形式を片方だけ直して
気付けなくなる。共用したことで、ワイヤ形式のテストが 1 本で両方に効く。

**中止はチャンクが届いた時点で効く。** 黙り込んだ接続先を相手にしているときだけ、
読み取りが返るまで畳まれない（fetch の「中止しています…のまま返ってこない経路」と
同じ割り切り。§8.3）。ストリーミングにしてあるので、生成が進んでいる限りは即座に効く。

#### 10.7.2 T-23 の目視で足したこと（2026-09-06）

**目視は通ったが、触ってみて 2 つ足りないことが分かった**（どちらも利用者の指摘）。
どちらも「動かない」ではなく**読めない／届かない**という形の指摘である。

**1. 何をレビューしたのかが画面に無い。** 履歴には日時とモデルしか出していなかったので、
同じリポジトリを何度もレビューすると**どれがどれだか読めなくなる**。
結果・履歴・Markdown の 3 か所に**リポジトリ名と対象**（コミット ＋ 要約 ／ 2 点比較 ／
作業ツリー）を出す。組み立ては純関数 1 つに閉じる（`src/lib/reviewTarget.ts`）。

**コミットの要約は保存していない。** 保存した JSON に足すこともできたが、
**すでに積んである履歴が読めるようになるほう**を取り、読み込み済みのコミットから引く。
引けなければ SHA だけになる（消えたコミット・読み込み範囲の外）。
足りなくなったら `StoredReview` の包む側へ控えを足せばよく、そのときも
文言の組み立ては同じ純関数のままにできる。

**2. 指摘を押しても行まで行かない。** T-23 では「ファイルを開くところまで」で
割り切っていたが、**ドロワーをコミット情報の列と入れ替える判断の根拠**が
「指摘から差分へ飛べる」だった（§6.1）ので、そこが弱いままだった。
指摘の行そのものを押せるようにし、差分の該当行まで動かして**印を残す**
（動いただけではどれが目的の行か分からない）。

- 飛び先は**行ではなく行リストの索引**で指す（仮想スクロールなので DOM に無い行は掴めない）。
  索引を引くのは純関数（`lib/diffRows.ts` の `rowIndexForLine`）
- **この差分に無い行を指した指摘では動かさない。** 近くの行へ寄せると
  **別の行の指摘に見える**（バッジを出さないのと同じ理由。CLAUDE.md §6）。
  代わりに**ドロワー側へ「この差分に無い行を指しています」と書く** —
  押しても何も起きないように見えるのを避ける。分かるのは
  **いま開いているファイルのぶんだけ**で、開いていないファイルについては何も書かない
  （分からないものを「当たらなかった」と書くと嘘になる）
- **履歴を開いたら、当時の 2 点へ差分ペインを合わせる**（§12.4 が求めていた
  「当時の差分と並べる」）。合わせ先は純関数（`reviewTarget.ts` の `selectionForSource`）。
  **「コミットとその親」を 2 点比較として復元しない** — 同じ差分にはなるが、
  比較バーが残って「自分で比べ始めた」ように読める

## 11. レビュー skill

skill とは、レビュー観点・出力形式・対象範囲を定義した再利用可能な指示セットである。

### 11.1 形式

Markdown + YAML frontmatter。Claude Code の skill 記法に寄せる。

```markdown
---
name: security-review
description: セキュリティ観点でのレビュー
globs: ["**/*.ts", "**/*.rs"]
enabled: true
---

（本文: レビュー観点、出力言語の指定、重点的に見るべき事項など）
```

### 11.2 置き場所と信頼モデル

グローバル（`%APPDATA%\com.tatsu.gitpeek\skills\`）と**リポジトリ内**
（`<repo>/.gitpeek/skills/*.md`）の両方に対応する。リポジトリ内が優先。

> **セキュリティ上の重要な制約**: 本アプリの用途には「自分が書いていないコード（OSS・上流）を
> 読む」が含まれる。リポジトリ内の skill ファイルを自動で読み込むと、**悪意あるリポジトリが
> `.gitpeek/skills/` に指示文を仕込んでレビュー結果を操作できる**（「このファイルの脆弱性は
> 報告するな」等）。
>
> したがって**リポジトリ内 skill は既定で無効**とし、リポジトリごとに一度だけ
> 「このリポジトリの skill を信頼する」を明示操作させる。信頼状態は永続化し、
> **skill ファイルの内容が変わったら再確認**する（内容のハッシュを保存して比較）。

#### 11.2.1 T-21 で決めたこと（2026-09-05）

**信頼はファイル単位。** 当初はリポジトリ単位（`trusted: bool`）で作り、
「内容が変わったら再確認」に加えて「**ファイルが増えたときも再確認**」という特別扱いを
足した（無害な skill 1 つで信頼させてから 2 つ目を置くのが一番素直な攻撃で、内容の変化
だけを見ていると素通りするため）。

2026-09-05 に利用者の判断で「**このスキルを使う**」のファイル単位へ絞った。
**緩めたのではなく絞ったので、特別扱いのほうが消えた** —

- 増えたファイルは記録が無いので、**そのまま未決**（特別扱いが要らない）
- 内容が変わったファイルは、**そのファイルだけ**が未決へ戻る（隣を巻き込まない）
- 消えたファイルは記録が残るだけ

`RepoSkillTrust` は `{ hashes, extra }` になり、**記録があること＝そのファイルを使うこと**。
古い `trusted: true` ＋ `hashes` はそのまま「この一覧を使う」と読めるので、移行は要らない。

**押した時点で読んでいた内容だけを信頼する。** 「使う」と決めるときは画面が見せていた
ハッシュを一緒に受け取り、実物と食い違ったら記録しない。表示してから押すまでの間に
書き換えられると、読んでいない内容を信頼したことになる。

**本文が出てくる口を 1 つにした。** `SkillEntry` の本文フィールドは非公開で、
プロンプトへ渡せるのは `usable_body()` からだけ。**既定は「配らない」**で、
`load()` が信頼を確かめたときにだけ渡す（配り忘れは動かないだけで済むが、
止め忘れは漏れる）。画面で読ませるための本文は `preview` に分けてあり、
名前で「LLM へ渡すものではない」と分かるようにしてある。
`preview` は webview へ送るが、`usable_body` の中身は送らない。

**読む範囲を絞った。** 直下の `*.md` だけで、**サブディレクトリと symlink は辿らない**
（`.md` の名前で `id_rsa` を指されると、その中身がプロンプトへ入る）。
1 ファイル 64 KiB / 1 か所 64 件を上限とし、超えたものは**読まずに理由付きで一覧へ残す**。

**同名の勝ち負けは信頼と選択を通ったあとで決める。** 「リポジトリ内が優先」と
「決めるまで使わない」は衝突するので、**勝てるのは実際に使うものだけ**とした。
使わない skill が同名の別のものを押しのけると、決めていないだけで何も使えなくなる。
どちらが効いているかは一覧に必ず出す — 同名でグローバルを差し替えられるのは、
「使う」を押して利用者が引き受けたことのはずで、黙って起きてはいけない。

**skill ごとの「追加の指示」を `settings.json` に持つ。** 本文の後ろへ足すだけで、
**skill ファイルは書き換えない** — 他人のリポジトリの skill にも足せるし、信頼のハッシュも
壊れない。`usable_body()` が本文と一続きにして返すので、**未信頼の skill には付かない**
（本文ごと出てこない）。利用者が書いたものなので、これ自体は信頼判定の対象ではない。

**frontmatter は 4 キーの厳格なサブセットを自前で読む。** `name` / `description` /
`globs` / `enabled` 以外のキーや読めない行があれば、**その skill ごと弾いて理由を出す。**
黙って既定値へ倒すと、レビュー観点が意図と違うまま静かに使われる。
`globs` は読み込み時に `globset` でコンパイルして検証する — 通しておかないと
「一覧には出るが 1 件も当たらない」という気付けない壊れ方をする。

**内蔵 skill は `include_str!` でバイナリへ埋め込む。** `%APPDATA%\skills\` へ書き出すと
「消しても復活する」「編集したものを更新で上書きする」の両方を抱える。

#### 11.2.2 画面の置き場所

**リポジトリに紐づくものを、アプリ全体の「設定」に混ぜない**（2026-09-05 に利用者の指摘）。
混ぜると、いまどのリポジトリの話をしているのかが画面から読めなくなる。

| 画面 | 出すもの | 入口 |
|---|---|---|
| アプリ全体の「設定」 | 内蔵 ＋ グローバルの skill ／ 接続先 ／ 表示・差分・fetch・レビューの設定 | ヘッダの「設定」と `Ctrl+,` |
| このリポジトリの設定 | そのリポジトリの中の skill ／ **既定の接続先** | リポジトリ一覧の**右クリック** |

一覧そのものは共通の部品（`SkillList.tsx`）で、出どころで絞って渡すだけにしてある。

**T-25（2026-09-06）で両側とも埋めた。** アプリ全体の設定は 1 枚のダイアログ（タブ 8 枚）に
なり、**ヘッダのテーマ選択と「接続先」ボタンもそこへ畳んだ**（入口が 3 つあると、
どこで何が変えられるのか読めない）。リポジトリ側には**既定の接続先**を足してある —
T-23 で覚えるようにしたのに画面から読めず、**勝手に変わっているようにしか見えなかった**
（clone の「この保存先を次回から既定にする」と同じ指摘）。

**可視 ref はここへ出さない。** ブランチツリーのチェックボックスがそのまま設定なので、
2 か所から変えられるようにすると、どちらが効いているのか読めなくなる。

### 11.3 適用

複数選択可。`globs` にマッチした skill を自動で有効化しつつ、実行前パネルで手動 on/off できる。

内蔵は「汎用コードレビュー（日本語出力）」1 つだけ同梱し、残りはユーザー定義とする。

#### 12.2.1 数値の範囲は 2 か所で締める（T-25。2026-09-06）

`settings.json` は**手編集を想定している**（CLAUDE.md §5）ので画面を通らない値が入るし、
Rust 側だけだと**打ち間違いが黙って書き換えられる**（画面には理由が出ない）。

**変えたら両方直す。** Rust 側のテスト（`normalizes_numbers_to_the_same_range_as_the_screen`）が
同じ数を見ているので、片方だけ変えるとそこで落ちる。

**画面は範囲外の値を保存しないだけで、書き換えない**（欄は消さず、理由を 1 行出す。
CLAUDE.md §6）。**読み込みのときに締めるのは Rust 側**で、こちらは
「値ひとつの打ち間違いでファイル全体を退避しない」ための緩衝。
**0 に意味がある欄（`fetch.staleWarningDays` = 警告しない）を 0 のまま通す**ことも
テストで固定してある。

### 12.4 レビュー結果の永続化

**保存する。** `reviews/<repo-id>/<日時>-<runId の先頭 8 桁>.json` に 1 レビュー 1 ファイル。

**同じ組み合わせで再実行しても上書きせず、履歴として積む。**
モデルや skill を変えて同じ差分をレビューし直し、結果を見比べたくなる場面が多いため。

リポジトリごとに「レビュー履歴」一覧を持ち、開くと当時の差分と並べて再表示する。
Markdown は出力専用（「Markdown で書き出し」ボタンで生成）。

#### 形は T-22 の `ReviewRun` をそのまま包む（T-23 で決めた。2026-09-06）

**当初はここに別の形の JSON を書いていたが、実装に合わせて書き直した。**
T-22 の `llm/review.rs` が返す `ReviewRun` が同じ内容を既に持っており、
**別の形へ変換すると変換器を両側に合わせ続ける**ことになるため（規約 4 の
「先行タスクの実装が正」）。包む側が足すのは 4 つだけ。

```jsonc
{
  "schemaVersion": 1,
  "repositoryId": "uuid",
  "savedAt": "2026-09-06T12:04:31+09:00",
  "file": "20260906T120431-1a2b3c4d.json",   // 自分の名前。一覧から開く鍵
  "profile": {                                // 実行時の控え
    "name": "local-qwen",
    "model": "qwen2.5-coder:14b",
    "baseUrl": "http://localhost:11434/v1"    // **redact 済み**
  },
  "run": { /* ReviewRun そのまま */ }
}
```

`ReviewRun` 側に、当初 §12.4 が求めていた情報は全部ある。

| 当初の案 | いまの居場所 |
|---|---|
| `from` / `to` / `diffMode` | `run.source`（`DiffSource`。作業ツリーも同じ型で表せる）|
| `skills` | `run.skills`（名前 ＋ 出どころ）|
| `profile` | 包む側の `profile`（**ID だけでは後から読めない**ので控えを残す）|
| `startedAt` / `finishedAt` | `run.startedAt` ＋ `run.elapsedMs` |
| `approxTokens` | `run.files[].tokensEstimate` の合計 |
| `failedCount` | `run.failed` |
| `structured` / `raw` | `run.files[].text.markdown`（**入っていれば構造化に失敗**）|

**プロファイルの `baseUrl` は `redact` を通してから書く**（§13.4 / CLAUDE.md §4）。
`https://user:token@host` を貼られていても平文で残さない。

**保存するのは Rust 側（`start_review` の中）。** フロントに保存させると、
例外や画面遷移で**保存し忘れる経路**ができる。**中止したレビューも積む** —
途中まででも読む価値があり、捨てるほうが損。一覧には「中止」と出す。

**一覧は壊れた 1 件で落とさない。** 読めないファイルと、`schemaVersion` が
将来版のファイルは、**理由付きで一覧に並べる**（skill の一覧と同じ扱い。§11.2.1）。
黙って消すと、あったはずの結果が無いのか壊れているのか区別が付かない。

## 13. エラー処理・ログ・診断

### 13.1 起動シーケンス

1. git を検出。失敗なら git 未検出画面（インストーラ導線＋パス手動指定＋再チェック）
2. 成功なら `state.json` から前回開いていたリポジトリを復元して自動で開く
3. パスが消えていたら一覧上でグレーアウトしたうえで空状態画面へ

### 13.2 空状態

リポジトリが 1 つも登録されていないときは、「リポジトリを追加 / フォルダをスキャン / URL から
clone」の 3 ボタンを中央に置く空状態画面を出す。チュートリアルは作らない。

LLM プロファイルが未設定のまま AI レビューを押した場合は、ボタンを無効化せず、押したら
「LLM プロファイルが未設定です」ダイアログから設定画面へ直行させる
（無効化＋ツールチップは理由が伝わりにくい）。

### 13.3 ログ

- **ログファイルを書く**: `logs/gitpeek-YYYY-MM-DD.log`、7 日分でローテーション。
  Phase 6 以降の認証・checkout まわりの問題は再現が難しく、後から追える記録が要る
- **画面上の git コマンドログ**は直近 500 件のリングバッファ。リポジトリ切替でクリアしない
- **Rust 側の panic はキャッチしてエラーダイアログを出し**、ログの場所を案内する

#### 13.3.1 T-24 で決めたこと（2026-09-06）

**`tauri-plugin-log` を足した**（利用者の判断）。自前で書く案（依存ゼロ）と並べて聞き、
プラグインを選んだ。**依存は `tauri-plugin-log` と `log` の 2 つ**で、npm 側は増やして
いない（フロントの例外は自前のコマンド 1 つで Rust へ渡す）。

決めたことは 5 つ。

- **書き出しの口は `logging::format_line` の 1 つだけ。** プラグインの `format` に
  これを差し込んであるので、`log` へ流れたものは全部ここを通る（§13.4.1）
- **書くのは「何が起きたか」だけ。本文は書かない。** プロンプト・差分・レビュー本文・
  skill 本文を書くと `%APPDATA%` に他人のソースと秘密が残る。LLM は接続先・モデル・
  所要時間・結果の種別まで。**git の stderr は全文残す**（利用者の判断。認証まわりは
  再現が難しく、1 行目では足りない）
- **置き場所は `%APPDATA%\com.tatsu.gitpeek\logs\`。** プラグイン既定の `LogDir` は
  Windows では `%LOCALAPPDATA%` を指すので使わず、`Folder` で明示する（CLAUDE.md §5）
- **古いものを消すのは自前の掃除（7 日）だけ。** プラグインの回転には消させない
  （`KeepAll`）。**消してよいのは `gitpeek-YYYY-MM-DD` で始まり `.log` で終わるもの**
  に限り、フォルダに置かれた他のファイルには触らない
- **書けなくてもアプリを止めない。** 代わりに画面へ 1 度出す（`LogStatus`）。
  黙って落とすと「書いているつもり」になる

**割り切りが 1 つ。日付は起動した日で固定される。** プラグインは書き出し先を
組み立てのときに決めるので、起動したまま日付をまたぐと同じファイルに書き続ける
（掃除は次の起動で追いつく）。1 日 1 本に収まるよう上限は 8 MiB にしてある
（プラグイン既定の 40 KB では 1 日に何度も分かれる）。

**「ログフォルダを開く」は capability を広げずに実装した。** `tauri-plugin-opener` は
導入済みだが、`opener:allow-open-path` を足すと**画面側から任意のパスを開ける**ように
なる。開くのは Rust 側のコマンドに閉じ、**パスはフロントから渡さない**
（開けるのはログフォルダだけ）。

### 13.4 秘匿情報のマスキング（必須）

**出力する全文字列に対して、`://<user>:<secret>@` パターンと API キーらしき文字列を正規表現で
マスクしてから記録する。画面表示とログファイルの両方に適用する。**

`git remote -v` の出力や git の stderr には、認証情報が URL に埋まっていると平文で出る。
それをそのままログファイルに書くと `%APPDATA%` に平文トークンが残る。

実装上は、**すべてのログ出力と画面表示が単一のマスキング関数（`redact.rs`）を通る**構造にする。

#### 13.4.1 適用範囲の点検（T-24。2026-09-06）

**どこを通って画面とログへ出るのかを数え上げ、通っていない口を塞いだ。**
規則は「**その文字列を組み立てるところで 1 度だけ通す**」で、
呼び出し側が忘れても漏れない形にしてある。

| 出どころ | 通す場所 | 備考 |
|---|---|---|
| git の stderr（**全経路**）| `git/exec.rs`（`GitOutput` を組み立てるところ）| **T-24 で足した。** それまでは `git/ops.rs` が個別に通していたので、そこを経由しない画面表示（`GitOutput::failure` / `git/detect.rs` / `git/repo.rs`）が生のままだった |
| git の起動失敗・引数 | `commandlog.rs` の `record()` | 引数にも URL が入る（`fetch <url>`）|
| fetch / clone の進捗行 | `git/ops.rs`（`Line::Body`）| 進捗は stderr を流し読みする別経路 |
| LLM の応答・エラー | `llm/client.rs` の `sanitize`（`redact` ＋ 使ったキー自体）| 規則に当たらない形のキーもここで伏せる |
| 流れてくる差分（ストリーミング）| `llm/client.rs` の `Masker` | チャンクの切れ目で割れた秘匿情報も拾う |
| レビュー結果の `baseUrl` | `store/reviews.rs` | 保存ファイルに平文を残さない |
| `settings.json` の読み込み失敗の理由 | `store/settings.rs` | ファイル名や理由に URL が乗りうる |
| **ログファイルの全行** | `logging.rs` の `format_line` | **T-24 で足した口。** ここを通らずに書ける経路を作らない |
| Rust の panic | `logging.rs` の `panic_line` | ペイロードに URL が乗りうる |

**git 自身が伏せてくれることを当てにしない。** 実測では、`git fetch <資格情報付き URL>`
の失敗メッセージから git が資格情報を落としていた（2.43）。**落とさない経路もある**
（知らないオプションを渡すと、受け取った文字列がそのまま stderr に出る）。
テストはこちらの形で書いてある — **git が伏せてくれる形で試すと、
マスクを外しても緑のまま通ってしまう。**

**stdout は通していない。** リポジトリのファイル内容そのものなので、
マスクを掛けると差分が壊れる。`git remote -v` のように**資格情報が stdout に出る
コマンドは、いま画面へ素通ししていない**（リモートの有無しか見ていない）。
出すようになったら、そのときに組み立てるところで通すこと。

---

### 13.5 白い画面を作らない

**フロントで例外が出たときに何も表示されない状態を作らない。** React は描画中に例外が出ると
木ごと外すため、受け止める場所が無いとウィンドウが真っ白になり、原因の手掛かりも残らない。
受け皿を 2 段構えで置く。

| 失敗する場所 | 受け皿 |
|---|---|
| モジュールの取得・評価（React が一度も動かない） | `index.html` のインラインスクリプト |
| 描画中の例外 | `src/components/common/ErrorBoundary.tsx` |

`index.html` 側は `error`（capture 付きで resource error も拾う）と `unhandledrejection` を見て、
`#root` が空のままなら理由を書き込む。10 秒経っても空なら「時間内に組み上がらなかった」と出す。
**この受け皿の文言だけは `src/i18n/ja.ts` に置けない**（ja.ts を読めない状況を扱うため、
インラインで持つ）。

なお、dev サーバ自体に到達できない場合（`npm run dev` が立っていない、ポート 1420 が別プロセスに
取られている）は HTML すら配信されないので、この受け皿も動かない。WebView2 のエラーページか
白い画面になる。`tauri dev` の出力に `Port 1420 is already in use` が出ていないか先に見ること。

---

**アプリ側で手当てできない白画面が 1 つある。** フィルタリング系ソフトが WebView2 の
ページに content script を差し込む場合、その問い合わせが返るまでページの評価が止まる。
実測（AdGuard 8.0.5560.0）では `injections.adguard.org` への要求が 29 秒返らず、
その間 `index.html` のインラインスクリプトすら動かなかった（HTML 自体は 33ms で届いていた）。
**受け皿は「自分のコードが動き始めた後」しか守れない**ので、これは環境側で外すしかない
（CLAUDE.md §10）。原因の切り分けには WebView2 のリモートデバッグが使える:
`WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS=--remote-debugging-port=9222` を付けて起動し、
`http://127.0.0.1:9222/json` でページの状態を見て、CDP で
`performance.getEntriesByType("resource")` を取る。

## 14. テスト戦略

### 14.1 レーン割り当てアルゴリズム（必須）

このアプリの心臓部であり、かつ目視デバッグが最も辛い部分（グラフが崩れても「なんとなく変」としか
分からない）なので、テストの投資対効果が突出して高い。

手書き DAG フィクスチャで期待レーン配列を検証する。最低限のケース:

- 直線的な履歴
- 単純な分岐と合流
- 連続するマージ
- オクトパスマージ（親が 3 つ以上）
- ルートコミットが複数ある履歴
- **lane 0 の幹予約が守られること**
- **可視 ref を絞ったときの再計算が正しいこと**

### 14.2 git 出力パーサ（必須）

実際の `git` 出力を固定文字列として持つ。異常系を必ず含める:

- 日本語ファイル名
- 空の subject
- 複数親
- 署名付きコミット
- 改行を含む subject

### 14.3 結合テスト

**生成する形の一覧はスクリプト先頭のコメントが正**（ここには写さない。写すと必ずずれる）。
形を足すときはスクリプトとそのコメントの両方に足し、レーンに関わるものは
`tests/lanes.rs` の一覧にも入れる。

- フロントは**純関数だけ**テストする。**対象は `src/lib/*.test.ts` が正**（`*.ts` と対で置く）。

  出し分け・検証・整形をそこへ直書きしないこと（clone の「既定の保存先」は直書きしたせいで、
  **条件が常に成立せず一度も表示されないまま**コマンドの受け入れ条件を全部通した）

### 15.1 Phase 2 が最初の判定ポイント

**Phase 2 完了時点で「美しいグラフ」の合否を判定する。**
不合格なら、この時点で §5.1（レーン割り当て）と §5.2（描線と配色）の決定に戻る。
後の Phase を作ってからでは戻れなくなる。

**判定は 2026-09-03 に合格した。** 対象は vite (10,186) / drogon (2,298) / onyx (20,285)。
目視 3 巡で 4 件直している（ホバーの背景がグラフを覆う / 横スクロールで列見出しがずれる /
ライトのレーン色が暗い / ルートで終わったレーンの再利用）。
**これで §5.1 と §5.2 の決定は確定とし、以降の Phase では動かさない。**

**T-08（判定ゲート）で測ったこと（2026-09-03）**

対象は onyx（20,285 コミット / マージ 597 件 / リモート追跡ブランチ 1,835 本 / タグ 2,374 個）。

- **第 2 親を「既に同じ親を待っているレーン」へ合流させる案は採らない。** 第 2 親の辺 597 本の
  うち合流できるのは 179 本だが、**そのうち 109 本の合流先は lane 0（幹）**で、幹の予約を
  破らずに合流できるのは 70 本しかない。実装して測った効果は max_lane 49 → 45、同時レーンの
  平均 11.43 → 11.17 と小さく、一方で合流する辺の **128/179 は左向き**、最大で 39 レーンぶんを
  横断する。細い線が画面を大きく左へ横切るほうが害が大きいので、
  §5.1-3（第 2 親は右に新レーンを起こす）を維持する。
- **`RESERVE_ROWS` は 2 のまま。** 1 / 2 / 3 / 4 のどれでも onyx の max_lane は 49、
  同時レーンの平均は 11.43 で**まったく変わらなかった**（枝が多い履歴では常に右に空きがあり、
  数行の保留は幅に響かない）。保留を伸ばすと「解放から数行以内の再利用」は確実に減る

## 付録 A. 使用する git コマンド一覧

すべて §3.1 の固定オプションと §3.2 の環境変数を付けて実行する。

| 用途 | コマンド |
|---|---|
| バージョン検出 | `git --version` |
| リポジトリ判定 | `git -C <path> rev-parse --absolute-git-dir --is-bare-repository --is-shallow-repository` |
| 作業ツリーの場所 | `git -C <path> rev-parse --show-toplevel`（bare では呼ばない） |
| リモートの有無 | `git -C <path> remote`（放置警告を出してよいかの判断 — §8.3） |
| **コミットメタ一括取得** | `git -C <path> log --branches --remotes [HEAD] --topo-order -z --format=<fmt>` |
| ref 一覧 | `git -C <path> for-each-ref --format=<fmt> refs/heads refs/remotes refs/tags` |
| HEAD 判定 | `git -C <path> symbolic-ref -q --short HEAD` / `git -C <path> rev-parse -q --verify HEAD` |
| 作業ツリー状態 | `git -C <path> status --porcelain=v2 -z` |
| コミット本文 | `git -C <path> show -s --format=<fmt> <sha>` |
| 変更ファイル一覧 | `git -C <path> diff --raw --numstat -z -M [--cached] <A> <B>` |
| 〃（ルートコミット）| `git -C <path> diff-tree --raw --numstat -z -M --root --no-commit-id -r <sha>` |
| ファイル差分 | `git -C <path> diff -M -U<N> [-w] <A> <B> -- <path>` |
| ステージ済み差分 | `git -C <path> diff -M -U<N> --cached` |
| 未ステージ差分 | `git -C <path> diff -M -U<N>` |
| バイナリのサイズ | `git -C <path> ls-tree -l -z <rev> -- <path>`（増減を出せないので大きさだけ） |
| コミットメッセージ全文 | `git -C <path> show -s --format=%B <sha>`（コピー用。**`%s` は最初の段落を 1 行に潰す**） |
| fetch | `git -C <path> fetch --all --prune --tags --progress` |
| checkout（ローカルブランチ）| `git -C <path> checkout <短い名前>` |
| checkout（それ以外）| `git -C <path> checkout --detach <完全な ref 名 または SHA>` |
| checkout（追跡ブランチ作成）| `git -C <path> checkout -b <名前> --track <完全な ref 名>`（**確認画面で選ばれたときだけ** — §8.1） |
| FF マージ | `git -C <path> merge --ff-only <ref>` |
| clone | `git clone --progress [--recurse-submodules] <url> <dir>`（**`-C` を使わない** — まだ無いフォルダを作る操作なので、保存先は絶対パスで渡す。`--recurse-submodules` は**確認画面でチェックされたときだけ** — §8.4）|

ahead/behind は git を呼ばずメモリ上のグラフから計算する（§4.5）。
**追跡ファイルの内容は `git show <rev>:<path>` では読まない。** 差分は `git diff` の出力から
組み立て、作業ツリーのファイルはディスクから直接読む（§7.5）。

**`<fmt>` の書式言語はコマンドごとに違う。** `git log` は `%x1f`（`%x` ＋ 16 進 2 桁）で
区切り文字を出すが、`for-each-ref` は `%x1f` を展開せず、16 進 2 桁だけの `%1f` を使う
（git 2.43 で実測）。取り違えると、区切りのつもりの `%x1f` が文字列のまま出力に混ざる。

**`git log` に `HEAD` を渡すのは HEAD がコミットを指しているときだけ。** コミット 0 件の
リポジトリに渡すと `fatal: ambiguous argument 'HEAD'` でコマンド全体が失敗する。
`--branches --remotes` だけなら exit 0 で空が返る。

**`refs/remotes/origin/HEAD` は `for-each-ref` の `%(symref)` で拾う**ため、`symbolic-ref` を
別に呼ばない。symbolic ref を ref 一覧から外さないと、`origin/main` がブランチとして二重に見える。
