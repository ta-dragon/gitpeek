## 1. 製品定義

Givsoner は**作者専用の Git ビューワー**である。コミット操作は一切行わない。

作者は git を CLI で操作する派であり、GUI からコミットする意思がない。したがって本アプリは
「git の書き込み操作を GUI に持ち込む」方向には一切拡張しない。これは機能の不足ではなく、
**明示的な設計上の境界**である。

主用途は次の2つ:

- **(a) 自分が書いていないコードを読む** — OSS、上流リポジトリ、他人の変更
- **(b) 複数リポジトリの状況を横断的に把握するダッシュボード**

git に対して書き込みを行うのは **checkout / fetch / fast-forward マージ / clone** の4つのみ。

### 1.1 恒久的に非対象とするもの

以下は「まだ作っていない」のではなく「作らないと決めた」ものである。

| 非対象 | 理由 |
|---|---|
| あらゆるコミット操作（commit / amend / rebase / cherry-pick / revert） | 製品定義そのもの |
| stage / unstage / discard / stash の作成・適用 | 作業ツリーは read-only。ビューワーが未保存作業を壊す経路を構造的に断つ |
| `--force` 付き checkout、自動 stash | 同上 |
| 非 fast-forward マージ | 競合解決 UI を持たない以上、中途半端に着手すべきでない |
| shallow clone (`--depth`) | 履歴グラフの閲覧が目的であり、浅いクローンは本末転倒 |
| 自動更新、コード署名 | 配布先が作者のみ。運用コストが見合わない |
| Gravatar 等の外部通信 | オフライン動作とプライバシーを損なう |

**10 万コミット超のモノレポはここに含めない。** v1 の設計（全件をメモリに載せてフロントへ渡す、
§4.1）と両立しないだけで、作らないと決めたものではない。**100 万コミット級の正式対応は
v1.1 以降で行う**（task_lists.md の「v1.1」表）。v1 では自動で読みに行かず、明示的に
選ばれたときだけ読む（§4.1）。

## 2. 技術スタックと配布

### 2.1 スタック

- **Tauri v2**（Rust バックエンド）＋ **React + TypeScript + Vite**（フロントエンド）
- コミットグラフは**自前のレーン計算 + SVG 描画**。既製グラフライブラリは不採用。

### 2.2 「美しいコミットグラフ」を最優先した結果としての選択

本アプリを作る第一の動機は「コミットグラフを美しく表示すること」である。この一点から
形態と描画方式を逆算した。

グラフの美しさを決めるのは次の3点である。

1. 任意の曲線を高 DPI で滲まずに引けるか
2. ホバー / クリックの当たり判定が安く取れるか
3. ライト / ダークのテーマ切替が容易か

**SVG はこの3点をすべて無料で満たす。** ベジェ曲線、CSS 変数によるテーマ切替、DOM イベントに
よる当たり判定がそのまま使える。

- **Canvas** は描画こそ速いが、DPI 対応・当たり判定・テキストをすべて手書きになる。しかも
  数万コミットあっても実際に描画するのは可視範囲の数十行だけなので、速度の利点が効かない。
- **WebGL** は過剰。
- **TUI** は文字グリッドであり、曲線が原理的に引けないため失格。
- **ネイティブ GUI（WinUI / Qt）** は描画自体は可能だが、シンタックスハイライト付き差分と
  AI の Markdown 出力を綺麗に出すエコシステムが Web に比べて著しく弱い。
- **VS Code 拡張**は「エディタを開いている」前提が必要になるため、作者の希望により除外。

容器として Electron ではなく **Tauri v2** を選んだ理由。

- 配布サイズが1桁 MB（Electron は 100MB 超）
- 常駐メモリが Electron の 1/3〜1/2。複数リポジトリを常時監視する性質のアプリでこれが効く
- Rust 側で git サブプロセスの並行実行とストリーミング出力の扱いが素直
- 環境が完全に揃っている（§2.4）

既製グラフライブラリ（`@gitgraph/js` 等）を採らない理由。これらは自前のレイアウトと描画を
抱えており、仮想スクロールおよび「レーン割り当てを自分で制御する」という本アプリの中核要件と
正面から衝突する。

### 2.3 アプリ識別と配布

- アプリ名: **Givsoner**
- bundle identifier: **`com.tatsu.givsoner`**
- `productName`: `Givsoner`、ウィンドウタイトル: `Givsoner — <リポジトリ名>`
- 配布は**ポータブル zip のみ**

> **注意**: Tauri v2 の bundler が Windows 向けに吐けるターゲットは `nsis` と `msi` だけで、
> **zip ターゲットは存在しない**。したがって「ポータブル zip」は `tauri build` が生成する
> `src-tauri/target/release/Givsoner.exe` を自前で zip 化する手順になる。単一 exe で動作する
> （WebView2 Runtime はシステム側にインストール済みのものを使うため同梱不要）。
> この zip 化は npm script として用意する。

- 自動更新（Tauri updater）は入れない
- コード署名しない（初回起動時に SmartScreen 警告が出るが「詳細情報 → 実行」で通す）

まず `rustup update stable` を試すこと。

## 3. git 実行方針

### 3.1 全 git 呼び出しに固定付与するオプション

```
git -c core.quotepath=false \
    -c core.autocrlf=false \
    -c core.pager=cat \
    -c color.ui=false \
    -c core.commitGraph=false \
    -C <repo> <subcommand> ...
```

| オプション | 理由 |
|---|---|
| `core.quotepath=false` | **未指定だと日本語ファイル名が 8 進エスケープされて返る。** 実測でこの環境は未設定＝デフォルト `true` であることを確認済み。付け忘れると日本語パスが全滅する |
| `core.autocrlf=false` | ユーザーの `.gitconfig` に左右されない決定的な挙動を得る |
| `core.pager=cat` | pager がサブプロセスで起動して固まるのを防ぐ |
| `color.ui=false` | ANSI エスケープが出力に混入するのを防ぐ |
| `core.commitGraph=false` | **本アプリの読み方では commit-graph が遅い**（下記） |

#### commit-graph を無効にする理由

commit-graph は「メッセージを読まずに履歴をたどる」操作のための索引である。ところが
Givsoner の主問い合わせ（§4.1 の全件ダンプ）は `%an`/`%ae`/`%s` を含むため、**どのみち
コミットオブジェクトを 1 件ずつ読む**。commit-graph を有効にすると、そこへ別ファイルへの
アクセスが上乗せされるだけになる。

Linux カーネル（1,481,526 コミット / pack 6.6GB）で、同一マシン・同一コマンドの A-B 計測:

| `core.commitGraph` | `git log --branches --remotes HEAD --topo-order -z --format=…` |
|---|---|
| `true` | 59.5 秒 |
| `false` | 19.0 秒 |

ahead/behind はメモリ上のグラフから計算する（§4.5）ので、commit-graph が本来効く
`rev-list --count` 系はそもそも呼ばない。**git は `gc` の際に commit-graph を自動生成する**
ため、明示的に切っておかないと、ある日を境に 3 倍遅くなる。

なお `%h`（短縮 SHA）の有無と `--topo-order` の有無は同じ計測で有意差が無かった
（`%h` を外して 16.7 秒、`%H` だけなら 14.6 秒）。**全件ダンプの時間はほぼコミットオブジェクトの
読み取りそのもの**であり、書式を削っても縮まない。

### 3.2 全 git 呼び出しに設定する環境変数

```
GIT_TERMINAL_PROMPT=0
GIT_SSH_COMMAND=ssh -o BatchMode=yes
```

**`GIT_TERMINAL_PROMPT=0` は必須である。** これが無い場合、認証が必要な場面で git は端末から
入力を読もうとする。GUI から起動した子プロセスには端末が無いため、**無言でハングする**。
`0` を設定すると `could not read Username for ... terminal prompts disabled` で即座に失敗するので、
アプリ側でエラーを整形して見せられる。

SSH も同様に、`BatchMode=yes` が無いとパスフレーズ入力待ちでハングする。

### 3.3 認証

認証は **git CLI に完全委譲**する。アプリはパスワードも Git のトークンも一切扱わない。

この環境では `credential.helper=manager` が設定済みで、GUI から `git clone https://...` を
起動すると Git Credential Manager が自前のウィンドウ（GitHub なら ブラウザ OAuth）を出し、
Windows 資格情報マネージャーにキャッシュする。2回目以降は無人で通る。

読み取りをライブラリ（gix / git2-rs）ではなく CLI に統一した最大の理由がこれである。
ライブラリを使うと認証・プロキシ・`.gitconfig` の全設定を自前で再実装する羽目になる。

### 3.4 git の検出と前提条件

- PATH の `git` を既定とし、設定でフルパス指定も可能
- **最低バージョン 2.20** を要求（現環境は 2.43）
- 未検出時は専用画面（公式インストーラへの導線＋パス手動指定欄＋再チェックボタン）

### 3.5 透明性 — git コマンドログ

**「git コマンドログ」パネルを常設する。** 実行した全コマンド・exit code・stderr・所要時間を
時系列で表示する（直近 500 件のリングバッファ、**リポジトリ切替でクリアしない**）。

理由。作者が git CLI 操作派である以上、「このアプリが裏で何を実行したか」が完全に見えることが
信頼に直結する。ビューワーがブラックボックスで git を叩くのは、この用途で最も嫌われる性質である。

エラー表示は常に「人間向けメッセージ ＋ 展開すると生 stderr」の2段構えとする。

**記録先は `commandlog::LogSink` として抽象化する**（T-02 で決定）。本番は `EmittingLog`
（リングバッファへ積み、`command-log` イベントでフロントへ送る）、テストは `CommandLog` を
そのまま渡す（積むだけ）。こうすると `git/exec.rs` が Tauri に依存せず、git を実際に起動する
結合テストが `AppHandle` 無しで書ける。`tauri::test::mock_app()` は Windows で
WebView2 の解決に失敗して使えなかった。

### 3.6 異常系

| 状況 | 扱い |
|---|---|
| 登録リポジトリのパスが消えている | 一覧でグレーアウトし「再指定 / 登録解除」を提示 |
| `.git/index.lock` が残留 | 検出して「他の git プロセスが動作中の可能性」を明示。**アプリ側から絶対に削除しない** |
| bare リポジトリ | 閲覧のみ許可し、checkout を無効化 |
| shallow クローン | 正常に表示（履歴が浅いことを明示） |
| detached HEAD | 正常表示 |
| コミット 0 件の空リポジトリ | 正常表示（空状態） |

## 4. データ取得とグラフのアーキテクチャ

### 4.1 全件一括取得

リポジトリ選択時に**全コミットのメタ情報のみを一括取得**し、**Rust 側でレーン計算まで確定**する。
フロントエンドの仮想スクロールは「確定済み配列の可視範囲を DOM 化する」役割に限定する。

差分・コミット本文・ファイル内容は選択時に遅延取得する。

**なぜページングではなく全件なのか。** 正確な topo-order グラフを描くには、原理的に
「対象 ref から到達可能な全コミットの親子関係」が事前に必要である。200 件ずつの増分読みでは、
後から現れた親でレーン割り当てが遡って変わり、**描画中にグラフが踊る**。グラフの美しさが本アプリの
存在理由である以上、これは許容できない。

**コスト見積。** 1 コミットのメタ情報は約 200B。3 万コミットで約 6MB、`git log` 自体も 3 万件で
数百 ms 〜 1 秒程度。十分現実的である。

この設計の帰結として、**v1 の想定規模は数万コミット / 数千ファイルを上限**とする。10 万コミット超の
モノレポは **v1 では非対象**（恒久的な非対象ではない。§1.1）。永続インデックス DB は持たない
（v1 の規模に対して複雑さが見合わない）。

非対象の側がどうなるかの実測（Linux カーネル 1,481,526 コミット / pack 6.6GB、リリースビルド）:

| 内訳 | 時間 |
|---|---|
| `git log` の実行と読み取りとパース | 17.4 秒（うち git 自体が約 16 秒） |
| JSON 直列化（450MB） | 0.7 秒 |
| 2 回目（ref の指紋が一致 → キャッシュ） | 0.13 秒 |

**時間のほぼ全部が git 自身**であり、こちら側の工夫では縮まない。

**450MB を IPC で webview へ渡す構造の方が、実は苦しい。** デバッグビルドでの実測で、
フロント側から見た往復は 39.7 秒（うち `git log` は 15.7 秒）。差の約 24 秒は直列化と転送と
`JSON.parse` であり、**その間 webview のメインスレッドは止まる**（ウィンドウが白いまま
描画されない時間が生まれる）。読み終えた webview は 1.5GB を保持する。

100 万コミット級を実用範囲に入れるなら「全件をフロントへ渡す」前提（本節）ごと見直しが要る。
**この見直しは v1.1 以降で行う**（task_lists.md の「v1.1」表）。v1 では見直さず、
**時間がかかっていることが分かる表示**で凌ぐ（§4.6）。

見直しの方向（v1.1 で詰める。ここでは決めていない）:

- レーン計算まで Rust 側で終える現状の構造を活かし、**フロントへ渡すのを可視範囲だけにする**
  （全件の JSON 直列化と `JSON.parse` が消える）
- コミットのメタ情報を Rust 側で持ち続け、行の取得をコマンド越しのページングにする
- 永続インデックス DB を持つかどうかは、上の 2 つで足りるか測ってから決める

**ただし非対象の規模を黙って読みに行かせない。** 148 万コミットのリポジトリを開いたまま
アプリを終了すると、次回起動時に自動で読み込みが走り、デバッグビルドで 60〜90 秒
操作できなくなったうえ、**givsoner.exe が 3.5GB・WebView2 が 3.2GB まで伸びて
プロセスが消えた**（エラー出力なし。空き物理メモリは 10GB 以上あった）。

そこで、**前回の件数が 10 万コミットを超えるリポジトリは自動で読み込まない**。
件数と所要時間の見込みを出し、明示的に選ばれたときだけ読む
（`src/store/snapshot.ts` の `LARGE_REPOSITORY_COMMITS`）。前回の件数が無い初回だけは
判断材料が無いので素直に読みに行く — 分母を得るのに `rev-list --count` を呼ぶと
`git log` と同じだけ待つことになり、本末転倒だからである。

なお**デバッグビルドでは JSON 直列化だけで 17.7 秒**かかる（リリースの約 28 倍）。
`npm run tauri dev` で測った数字をそのまま製品の性能と見ないこと。
リリースビルドで動かすには `npm run start:release`。

キャッシュは HEAD と全 ref の SHA をキーに無効化する。直前のリポジトリのグラフは LRU で 2〜3 件
保持し、切替を体感即時にする。

### 4.2 起点 ref — `--all` を使ってはいけない

グラフの起点は**全ローカルブランチと全リモート追跡ブランチ**、および HEAD とする。
**タグは起点 ref に含めない**（どのブランチからも到達不能な古いタグが孤立点として散らばるのを防ぐ）。

> **重要**: `git log --all` は「`refs/` 配下の全 ref、および HEAD」を起点にする。これは
> **`refs/tags/` も `refs/stash` も `refs/notes/` も含む**ため、上の決定に違反する。
> 正しくは次を使う。
>
> ```
> git log --branches --remotes HEAD --topo-order ...
> ```
>
> （`--branches` = `refs/heads/*`、`--remotes` = `refs/remotes/*`）

タグはコミット上のラベルとしては表示する。**タグの指すコミットが読み込み集合に含まれない場合**
（ブランチが消された古いリリースタグなど）は、タグツリーには表示するが「グラフ外」と印を付け、
ジャンプを無効化する。

### 4.3 並び順

**topo-order 既定 / date-order に切替可**。

切替時は `git log` を再実行しない。全コミットの親子関係と日時がメモリにあるため、
**メモリ上で並べ替えとレーン再計算のみ**で済む（数十 ms）。
date-order 表示時は「この表示では線が交差します」の注記を出す。

### 4.4 ブランチ表示 ON/OFF の意味論

チェックを外したブランチについて、**可視 ref 集合から到達可能集合を再計算してレーンを振り直す**。
行数も線の本数も実際に減る。

淡色化やラベル非表示ではなく再計算にした理由。解決したい痛みは「リモート追跡ブランチが 40 本
あって画面が線だらけ」であり、線の本数が減らなければ目的を達成しない。全コミットがメモリ上に
あるので、再計算は数万コミットでも数十 ms で済む。

プリセット: 全選択 / 全解除 / ローカルのみ / リモートのみ。選択状態はリポジトリごとに永続化する
（`settings.json` の `repositories[].visibleRefs`）。

**起点にするのはブランチと HEAD だけ。** タグは起点 ref にしないので（§4.2）、
タグのチェックはグラフの中身に影響しない。**HEAD は常に起点に入れる** —
`git log --branches --remotes HEAD` と揃えるためで、全部のチェックを外しても
今いる場所の履歴だけは残る（画面が空になるより手掛かりが残るほうがよい）。

**幹の ref を隠した場合も lane 0 は空けない。** 起点が絞った集合に残らなければ、
レーン計算は先頭コミットを幹として扱う（§5.1-1）。lane 0 を空けたままにすると
グラフ全体が 1 レーン右へずれる。

**タグにはチェックボックスを置かない**（T-10 で決定）。タグは起点 ref ではないので、
チェックを外してもグラフは 1 行も変わらない。「押せるが何も起きない」ほうが、
最初から無いより分かりにくい。タグはツリーに出すが、操作はジャンプとコピーだけにする。
`visibleRefs.excluded` にタグの ref 名が入ることは無い。

**絞り込みの結果はコミットリストの行数にも出る。** グラフだけを絞ってリストが全件のままだと、
行の文字と線が 1 行ずつずれる（§6.3）。

### 4.5 ahead/behind

**全ブランチの ahead/behind をメモリ上のグラフから計算する。**

`git rev-list --count` をブランチ数だけ呼ぶ実装だと、100 ブランチで 100 プロセス起動になる。
§4.1 で全コミットの親子関係を保持しているので、到達性計算で無料で求まる。

**比べる相手は上流**（`git branch -vv` と同じ）。上流の無いローカルブランチ、
リモート追跡ブランチ、タグは相手が決まらないので数値を出さない。
上流が `fetch --prune` で消えている場合も同じ。

数え方は**両側から同時に親へ下り、共通祖先に着いた時点で止める**。全体を舐めないので、
分岐が浅いほど速い（ふつうのブランチと上流の差は数コミット）。
ref ごとにビットセットを持つ実装は 20,000 コミット × 数千 ref でメモリが厳しいので採らない。

### 4.6 途中経過の見せ方

想定規模（数万コミット）では読み込みは 1 秒未満で終わる。**非対象の規模でも「固まった」と
思わせない**ことだけを目的に、途中経過を出す。

段階は取得の内訳そのもの。`Refs`（ref 一覧と HEAD）→ `Commits`（`git log` の全件ダンプ）→
`Graph`（到達可能集合と幹の決定）→ `Transfer`（直列化と転送）。

- **件数は `git log` の出力を読みながら NUL を数えて得る。** パースの完了を待たない。
  そのために `exec::run_streaming` があり、`Command::output()` と違って完了前に読み進める
- **割合の分母は前回の読み込み件数**（`state.json` の `lastCommitCount`）。初回は分からないので
  割合を出さず件数だけ流す。**嘘の割合を出すより、進んでいることが分かる方を採る**
- 報告は 150ms 間隔に間引く。300MB を 64KB ずつ読むと 5000 回近く呼ばれるため
- 表示は 400ms 経ってから出す。数万コミットではバーが一瞬光って消えるだけになる
- `Transfer` は**イベントを送ってから**返す。この段階で webview のメインスレッドは
  止まるので、止まる前に「何をしているか」を出しておく必要がある

進捗の受け口は §3.5 の `LogSink` と同じくトレイト
（`git::progress::ProgressSink`）にし、git 側のコードを `AppHandle` に依存させない。

## 5. コミットグラフの視覚仕様

### 5.1 レーン割り当てアルゴリズム

グラフの美しさの 8 割はここで決まる。

1. **lane 0 を幹に予約する。**
   既定ブランチ（`origin/HEAD` → 無ければ `main` / `master` → 無ければ現在の HEAD の順で決定）の
   第一親チェーンを lane 0 に予約し、**必ず一直線に描く**。
   幹が画面左端をまっすぐ通り、他がすべて枝として見えるため、可読性が劇的に上がる。

   **幹は起点より新しい側へも伸ばす。** 起点を第一親に持つ子を辿り、分かれ道では
   topo-order で先に来る子（画面で上に描かれる方）を採る。第二親でしか繋がらない子は
   幹にしない（マージで合流しただけの枝まで引き込むと lane 0 が枝へ乗り移る）。

   下方向だけを幹にすると、**既定ブランチより先へ進んだブランチを開いているときに
   画面上部が壊れる**。実測（AerialSoldierMaker、master より 9 コミット先の
   ブランチを checkout した状態）では、一直線の履歴にもかかわらず上 9 行が lane 1 を下り、
   master の行で lane 0 へ折れた。1 本の線が途中で折れているようにしか見えない。

2. **レーン再利用は最小空きレーンだが、解放直後の 1〜2 行は再利用を保留する。**
   即座に最小番号を再利用すると、1 本の線が交差直後に無関係なブランチへ「化ける」ように見える。
   逆にブランチが尽きるまで占有し続けるとレーン数が増えすぎる。その中間を取る。

   **ただしルートコミット（親なし）で終わったレーンは二度と配らない。**
   レーンの終わり方は 2 通りある。マージや「同じ親を待つレーンへの畳み込み」で終わる場合は、
   線が別レーンへ曲がって続くので、そこで終わったことが目に見える。**ルートだけは線が
   その場で止まる。** 数行後に同じレーンを別の枝が使うと、レーン色は同じなので
   **1 本の線が穴を空けて続いている**ようにしか見えない。
   実測（onyx、orphan ブランチ `origin/assets/...` のルート）では 2 行後に再利用されており、
   目視で「グラフが途中で切れている」と報告された。

   費用はほぼ無い。ルートはリポジトリに数個しかなく、onyx（ルート 4 個）で max_lane が
   49 → 52 に増えるだけで、同時レーン数の平均は 11.43 のまま変わらない。
   vite（ルート 1 個）と drogon（同）では**何も変わらなかった**（元々再利用されていない）。

3. **マージコミットの第 2 親は右側に新レーンを起こす。**

4. **レーン数に上限を設けない。**
   レーン幅を可変にして詰める方式は、密度が上がったときに確実に破綻する。

   **グラフは幅を持つ「列」として扱い、列幅より右のレーンは切る**（既定 200px、
   ドラッグ可変、リポジトリごとに `state.json` へ永続化）。全レーンぶんの幅を常に
   空けると本文が画面の外へ押し出される（onyx は 49 レーン ＝ 712px あった）。
   見出しの取っ手を引けば全レーンまで広がる。**横スクロールはリスト全体で 1 つ**にする
   （グラフ列だけ別にスクロールさせると行とずれる）。

### 5.2 描線と配色

- **線**: 垂直の直線を基本とし、**分岐 / 合流点のみ角丸ベジェ**
  （直角エルボーや斜め直線ではなく、最も柔らかい形状を選ぶ）。
  **曲がりに使う縦の長さは横の移動量に合わせて伸ばす。** 1 レーンぶんの移動では 8〜12px の
  角丸に相当する長さ（実装は `CORNER_RADIUS * 2` を下限とする）、それ以上またぐときは
  移動量と同じだけ縦を使う。固定長にすると、数レーンぶんの移動が 20px の帯に押し込まれて
  ほぼ水平の直線になる（onyx の実データで、1 行のあいだに 8 レーン移動する辺が 99 本あった）。
- **線は辺だけで描く。** 素通りするレーンの縦線を辺と重ねて引いてはいけない。
  素通りするレーンは必ず「上の行のノードから下の行の親まで」の辺に覆われているので、
  重ねると、辺が曲がって別レーンへ移った後に縦線だけが残り、**どこにも繋がらない
  線の切れ端**になる。仮想スクロールで窓が途中から始まる場合は、窓を跨ぐ辺を拾うこと。
- **走る余地の無い中間レーンは経由しない。** 第 2 親のために起こしたレーンが 1〜2 行で
  終わる場合（同リポジトリで 137 箇所）、そのレーンまで右へ跳ねてすぐ左へ戻る弧になり、
  グラフから飛び出して見える。縦に走る区間が無いレーンは通らず、直接繋ぐ。
- **配色**: レーン番号で **8 色をローテーション**。ただし **lane 0（幹）のみ無彩色寄りの固定色**に
  して幹を主張させる。パレットは彩度を抑え、ライト / ダークで別定義する。

  ブランチ名のハッシュで色を決める方式は不採用。§5.1-2 のレーン再利用と組み合わせると
  隣接レーンに似た色が並ぶ事故が起きやすく、結果的に汚くなる。

  **パレットの並び順は隣接レーンの色差で決める。** 隣り合う 2 レーンは配列上も隣り合う
  2 色になるので、順番を入れ替えるときは CIE Lab の色差がどの隣接組でも 60 以上あることを
  確かめること（T-08 の実測: olive と brown を隣に置くと 25.7 まで落ちて見分けがつかない）。

  **明るさはライトとダークで別々に決める。同じ色を使い回さない。** 白地に濃い色を置くと
  線が重く、グラフ全体が暗く沈む（T-08 の目視で指摘された）。ライトは **L\* 55〜60 /
  白との輝度比 3.1〜3.7**、ダークは **L\* 62〜74 / 背景との輝度比 5.7〜8.1** に揃える。
  ライト側の輝度比の下限は 3.0（WCAG 1.4.11 の非テキスト要素）。ホバー行の背景
  (#e7ebf1) の上でも 2.6 を切らないこと。**これ以上明るくすると線が見えなくなる**ので、
  「まだ暗い」と感じたら色ではなく線幅を疑う。

- **ノード**: 通常 = 直径 8px の塗り円 / マージ = 中空円 / HEAD = リング付き / 選択中 = 拡大＋発光 /
  **ルート（親なし）= ノードの下に短い横棒**。レーンの終わり方のうち、マージと
  「同じ親を待つレーンへの畳み込み」は線が別レーンへ曲がって続くので終わりが目に見えるが、
  **ルートだけは線がその場で止まる**。印が無いと「終わった」のか「切れた」のか分からない
  （§5.1-2）。横棒は行の高さとレーン幅の内側に収めること。はみ出すと隣の線を横切って見える
- **寸法**: 行高 28px、レーン幅 14px、ノード列の左マージン 12px（実装後に微調整）

### 5.3 ナビゲーション補助

**スクロールバー上に ref マーカーを描く**（ブランチ先端 = レーン色の短い線、タグ = 小さな菱形）。

数万コミットのリストではスクラバが極端に小さくなり位置感覚が完全に失われるため、
実装コストに対して効果が非常に大きい。ミニマップは作らない。

**同じ高さに重なるぶんは 1 本に束ねる。** onyx は ref が 3,790 個あり、そのまま置くと
12px の帯が塗り潰れるうえ DOM が 3,790 要素になる。トラックを固定数（300）に割り、
1 枠につき 1 つだけ描く。残すのは**ブランチ先端を優先**（タグより「今どこにいるか」の
手掛かりになる）。

## 6. UI 構成

### 6.1 レイアウト

```
+----------------+-------------------------------+----------------+
| リポジトリ一覧 |  コミットグラフ + コミットリスト| コミット詳細  |
|  (上段)        |                               |  (full message)|
|                +-------------------------------+                |
| ブランチ/タグ  |  差分本体                     | 変更ファイル   |
| ツリー (下段)  |  (side-by-side / unified)     |  一覧          |
+----------------+-------------------------------+----------------+
```

- 3 ペイン。中央だけ上下分割。境界ドラッグで比率可変、幅・比率とも永続化
  （`state.json` の `paneRatios.sidebarWidth` / `graphDiffSplit` / `commitInfoWidth`）
- 差分を side-by-side で見るには横幅が要るため、差分本体は**中央下**に置いて横幅をフルに使う
- **コミット詳細と変更ファイル一覧は右の列**に出す。**差分本体と縦に積まない。**
  積んでいたときは、詳細（本文＋作者＋親）と一覧が高さを食って差分に数行しか残らなかった。
  右へ出せば、一覧が何十行あっても差分の幅も高さも削らない
- 右の列は**縦に長い 1 列**なので、詳細は中身なり（上限つき）、一覧が残りを全部取る
- AI レビューは**さらに右のドロワー**（幅可変、閉じられる）。指摘を差分の該当行と対比しながら
  読めることが必要なため、モーダルや独立画面にしない。**開いている間はコミット情報の列と
  並べず、そちらを畳む**（T-23 で決める。3 列 ＋ ドロワーでは差分が潰れる）
- テーマは **OS 追従が既定**・手動切替可。作り込みはダーク優先
- UI 言語は**日本語固定**。ただし全表示文言を `src/i18n/ja.ts` に集約しキー参照する
  （i18n ライブラリは入れない。将来必要になったら差し替えるだけで済む形にしておく）

**Windows 固有**: `tauri.conf.json` の `app.windows[].dragDropEnabled` を **`false`** にする。
既定の `true` では WebView2 がファイルのドラッグ＆ドロップを先に掴み、**フロント側の HTML5
ドラッグ＆ドロップ（リポジトリ一覧の並べ替え）が一切動かない**（Tauri 本体のドキュメントに
「Disabling it is required to use HTML5 drag and drop on the frontend on Windows」と明記されている）。
引き換えに「フォルダをウィンドウへ落として登録」は使えなくなるが、v1 では非対象。

### 6.2 リポジトリ切替

- **常時サイドバー ＋ `Ctrl+P` で絞り込みジャンプ**の併用
- **タブは持たない**（1 リポジトリ 1 ビュー）。リポジトリごとに数万コミットのメタ情報をメモリに
  載せる設計と掛け算になるため。代わりに直前のリポジトリのグラフを LRU で 2〜3 件保持する
- 切替時の状態（選択コミット / スクロール位置 / ブランチ表示 ON/OFF / 開いていた差分）は復元する
- 並び順は手動 D&D ＋「最終アクセス順」表示のトグル。フォルダによるグループ分けは v1.1
- 一覧の各行に常時表示: 現在ブランチ名 / ahead・behind バッジ / dirty マーク / fetch 放置アイコン

### 6.3 コミットリスト

列構成: `グラフ | subject + ref チップ | 作者名 | 日時 | 短縮SHA`

- 列幅はドラッグ可変・永続化。列の増減は v1 では不可
- 短縮 SHA は `git log --format=%h` に委ねる（git 自身が衝突しない最短長を選ぶ）
- 日時は**既定で相対**（「3 日前」）、ホバーで絶対をツールチップ表示。設定で入れ替え可
- 作者は**名前のみ、アバターなし**。Gravatar はメールアドレスのハッシュを外部サーバに送るため、
  オフライン動作とプライバシーの両方を損なう
- ref チップが行に収まらない場合は「+N」に畳み、ホバーで全件表示
- **orphan ブランチ**（幹とコミットを 1 つも共有しない履歴）の ref チップは**破線の枠**にし、
  グラフのルート終端と同じ `⊥` を前置する。判定はコミット DAG の連結成分で行う
  （親子の向きを無視した無向グラフ。到達可能性 §4.4 とは別物で union-find 1 回）。
  **マージで合流した無関係履歴は orphan ではない** — 繋がっているので線も途切れない

**列見出しは行と同じスクロールコンテナに入れ、縦だけ `position: sticky` で貼り付ける。**
外に出すと、列の合計幅が窓を超えたときに見出しだけが動かず行とずれる。さらに、見出しの
最小幅がそのまま外へ伝わって親ペインに 2 本目の横スクロールバーが生える（T-07 の目視で
両方出た）。見出しの高さは `--head-height` で固定し、仮想スクロールには `scrollMargin`
として同じ値を渡す。行の上端へ寄せるスクロールは、貼り付いた見出しの下に潜らないよう
自前で計算する（`scrollToIndex` は見出しを知らない）。

**グラフは行の背景より前面に置く。** 背面に敷くと、ホバーや選択の背景（不透明）に線が
塗り潰されて消える。`pointer-events: none` なので前面でもクリックは下の行に届く。

**並べる順と件数の正は `LaneLayout.rows`** であって、読み込んだコミット配列ではない。
レーンは可視 ref で絞られ（§4.4）、date 表示では組み替わる（§4.3）。行の文字を
コミット配列の添字で引くと、どちらの経路でもグラフと 1 行ずつずれる（T-10 で発覚）。
`rows` を順に辿り、SHA でコミットを引くこと。

### 6.4 ブランチ / タグツリー

- `feature/foo` のようなスラッシュ区切りを**階層フォルダとして畳む**
  （同一プレフィックス配下が 3 件以上で自動フォルダ化、開閉状態は永続化）
- トップレベルは `ローカル` / `リモート > origin` / `タグ` の 3 グループ
- タググループは既定で折りたたみ。ツリー上部に絞り込み入力欄を常設（ブランチもタグも同じ欄で絞る）
- 各ブランチ行に ahead/behind を表示（§4.5）
- 右クリックメニュー: checkout / 現在のブランチに FF マージ / このブランチだけ表示 /
  このブランチの先頭へジャンプ / ブランチ名をコピー / SHA をコピー

**畳む閾値は 3 件**（`refTree.ts` の `FOLDER_THRESHOLD`）。2 件のために階層を 1 段深くしても
クリックが増えるだけで、`feature/a` `feature/b` は 2 行のまま出したほうが速く読める。
数えるのは**配下（パスが 2 段以上）だけ**なので、`feature` というブランチと `feature/` フォルダが
同じ階層に並ぶことがある。ブランチがフォルダに吸われるより、両方見えるほうが正しい。
**絞り込みは畳む前に効かせる** — 1 件に絞られたフォルダは消えて平らになる。

**リモートはリモート名でグループを分け、ブランチ名からリモート名を外す**
（`origin/feature/a` は `リモート > origin` の下に `feature/a` として出る）。
`origin` 以外のリモートがあれば、その数だけグループが増える。

**ahead/behind は 0 のとき何も出さない。** 上流を持たないブランチも同じく空欄にする
（§4.5 のとおり比べる相手が決まらない）。全ブランチに「上流なし」を並べると騒がしいだけなので、
差があるときだけ `↑2` `↓3` を出し、同期しているか上流が無いかはツールチップで見せる。

**グラフから外した ref は淡色にする。** チェックボックスは小さく、遠目にはどれを外したか
読み取れない。ここでの淡色化は §4.4 が退けた「グラフの淡色化」とは別で、
グラフ側の行は実際に消えている。

**開閉状態は「畳んだ ID」を保存する**（`state.json` の `collapsedTreeNodes`、§12.3）。
既定が「開いている」なので、この向きなら空配列が「すべて既定」を意味する。展開側を
保存すると、利用者が全部畳んだ状態と初期状態を区別できない。

checkout と FF マージは**項目としては出すが T-18 まで無効**にする。機能がどこにあるかだけ
先に示しておく。

**開閉の三角は文字ではなくボーダーで描く。** `▸` / `▾` は 10px では潰れて開閉が読めず、
2 つの字形を見比べる形になる（目視の指摘）。同じ三角を回転させれば、形は変わらず向きだけが
変わるので差が分かる。大きさをフォントに左右されないことも利点。

**ツリーとリポジトリ一覧の縦の取り合いは `flex-basis` で決まる。** ツリー側を `flex: 1 1 auto`
にすると、ref が数千本あるリポジトリ（vite / onyx）で中身の高さがそのまま基準サイズになり、
縮小が基準サイズの比で配分されて**リポジトリ一覧が 9px まで潰れた**（実測）。
スクロールするペインの基準は 0 にし、上段の「中身なり（最大 50%）」が先に決まるようにする。

### 6.5 キーボードショートカット（v1 で確定）

VS Code 風を基本に、リスト移動のみ vim 風の `j` / `k` も受ける。

| キー | 動作 |
|---|---|
| `Ctrl+P` | リポジトリ切替（絞り込み） |
| `↑` `↓` / `j` `k` | コミット移動 |
| `Enter` | 差分ペインへフォーカス |
| `Alt+↑` `Alt+↓` | 前 / 次のファイルへ移動 |
| `Alt+←` | 第 1 親コミットへ移動（親が複数なら選択メニュー） |
| `Alt+→` | 子コミットへ移動 |
| `Ctrl+H` | HEAD へジャンプ |
| `Home` / `End` | 先頭 / 末尾へ |
| `Ctrl+R` | 現在リポジトリを fetch |
| `Ctrl+Shift+R` | 全リポジトリを fetch |
| `Ctrl+Shift+A` | AI レビュー実行 |
| `Ctrl+F` | 差分内検索 |
| `Ctrl+,` | 設定 |
| `F5` | グラフ再読込 |
| `Esc` | ドロワー / パネルを閉じる |

ツールバーの入力欄に SHA を貼るとそのコミットへジャンプする（前方一致可）。

**この表は v1 の最終形であり、現時点で全部が効くわけではない。** T-11 完了時点で
効くのは `Ctrl+P` / `↑` `↓` / `j` `k` / `Alt+←` `Alt+→` / `Alt+↑` `Alt+↓` / `Enter` /
`Ctrl+H` / `Home` / `End` と SHA ジャンプ。残りは対応する機能を作る Phase で足し、
最後に T-25 で揃える。

実装は 2 箇所に分かれている。**コミットの移動は `src/hooks/useCommitNavigation.ts`、
ファイルの移動とフォーカス移動は `src/components/diff/useCommitFiles.ts`**。
ファイル一覧を持っているのがそのフックなので、そこで処理するほうが状態を渡さずに済む。
どちらも入力欄にフォーカスがあるときは横取りしない。

## 7. 閲覧機能（v1 範囲）

### 7.1 v1 に含めるもの

1. ブランチ / タグ / リモート追跡ブランチの一覧
2. コミットログとグラフ
3. コミット詳細と親との差分
4. **任意の 2 コミット間の差分**
5. 任意リビジョンのファイルツリー閲覧とファイル全文表示

加えて checkout / fetch / FF マージ / clone（§8）。

### 7.2 差分表示

- **レイアウト**: side-by-side / unified 切替可（既定 side-by-side）
- **word-level ハイライト**あり
- **シンタックスハイライトは Shiki**。VS Code と同じ TextMate 文法で精度が最も高い。差分の
  可読性がこのアプリの価値の半分を占めるため、初期ロードの重さより精度を取る。言語別文法は遅延ロード
- **リネーム検出は `-M` のみ**。`-C`（コピー検出）はコストが高く誤検出も多いため使わない
- **空白無視トグル**（`-w`）と**コンテキスト行の増減ボタン**（既定 `-U3`）
- **1 ファイル 3000 行または 500KB 超は既定で折りたたみ**、明示操作で展開。
  素朴に DOM 化すると簡単に固まるため
- **バイナリ**は「バイナリファイル（サイズ変化）」の表示のみ。画像差分は v1.1

**パースは Rust 側に置く**（`git/diff.rs`。T-13 で骨子から変更）。改行コードは**内容行だけ**を
数える必要があり（§9.2）、ヘッダ行と内容行を分ける時点でパースそのものになる。
バイト列と文字コード判別を持っているのも Rust 側なので、二重に持つ理由がない。
フロントに残すのは**行の対応付けと語単位差分**で、どちらも純関数（`src/lib/diffView.ts`）。

**リネームでは pathspec に古いパスと新しいパスの両方を渡す。** 新しいパスだけを渡すと
git は対になる側が見えずリネームを検出できず、**全行が追加された新規ファイル**として出す
（実測。`tests/diff.rs` の `rename_needs_both_paths_in_the_pathspec` が固定している）。

**side-by-side は 1 行を 1 つの grid にする。** 行ごとに 4 列（旧行番号 / 旧本文 /
新行番号 / 新本文）を置くので、本文が折り返しても左右が同じ行に留まる。
列を縦に 4 本並べる作りだと、片側だけ折り返した瞬間に以降が全部ずれる。
**対応する行が無いところは空欄**にし、行番号も出さない。

**本文は折り返す**（横スクロールにしない）。左右で別々に横スクロールさせると行が見比べられず、
1 本にまとめると親ペインに 2 本目のスクロールバーが生える（CLAUDE.md §6）。

**語単位ハイライトは共通の先頭と末尾を削るだけ**にする。文字単位（コードポイント単位）で削り、
共通部分が長いほうの 30% 未満なら行全体を変更として扱う。LCS を回さないのは、日本語では
語境界が取れないうえ、実際の差分は「行内の 1 箇所を直した」が大半を占めるため。
まるごと書き換えた行に細かいハイライトを出すと、共通の記号（括弧やカンマ）が飛び飛びに
残ってかえって読めない。

**表示の切替は `settings.json` の `ui` に残す**（レイアウト / コンテキスト行 / 空白無視 /
改行の可視化）。毎回選び直したくないため。**文字コードの手動上書きだけは残さない** —
ファイルごとの判断なので、別のファイルへ持ち越すと黙って化ける。

**コンテキスト行は 0 / 3 / 10 / 25 / すべて**から選ぶ。「すべて」は十分大きな `-U` で代用する。

**ダークの差分色は輝度比を測って決めてある**（CLAUDE.md §6「明るさもライト / ダークで別に決める」）。
最初はペインの地 (`--bg-inset`) との比が 1.2 程度しかなく、**特に緑が青みの強い地に埋もれて
変更行を見分けられなかった**（目視で戻した）。取り直した実測値:

| | 行の地 ÷ ペインの地 | 語の強調 ÷ 行の地 | 本文 ÷ 語の強調 |
|---|---|---|---|
| 追加（緑） | 1.59 | 2.23 | 4.22 |
| 削除（赤） | 1.43 | 1.92 | 5.47 |

ライトは白地なので同じ値にはできない。**入れ替えるときは両方測り直すこと。**

**シンタックスハイライトは Shiki を遅延読み込みする**（T-14）。`shiki` のフルバンドルを
import すると全言語の文法が 1 チャンクに入るので、`shiki/core` に**言語ごとの動的 import**を
渡す。正規表現エンジンの wasm もローカル import なので、**外部 CDN へは出ない**
（CLAUDE.md §1）。拡張子 → 言語は表で持ち、**Shiki の別名に頼らない** — 別名があるのは
一部だけで、`mts` や `hpp` を渡すと「そんな言語は無い」で落ちる。表に無い拡張子は
ハイライトしない（総当たりで文法を読むより素の本文のほうが速く、外したときの色崩れもない）。

**トークン化は hunk の片側ごとにまとめて行う。** 行を 1 本ずつ渡すと、複数行にまたがる
文字列やコメントが行ごとに切れて色が壊れる。変更前（context + removed）と変更後
（context + added）をそれぞれ 1 本のテキストに戻して渡し、行へ配り直す。

**トークンと語単位差分は合成する**（`dangerouslySetInnerHTML` で Shiki の HTML を
流し込まない）。両者の区切りは互いに無関係なので、両方の境界で切り直したセグメント列を作る。
長さが食い違ったらハイライトを捨てる — **行がずれるくらいなら色が無いほうがまし**。

**語単位の強調の中では構文色を使わない。** 強調の地色は行の地より明るいので、
その上に構文色（github-dark は #0d1117 前提、github-light は #fff 前提）を載せると読めない。
実測:

| | 強調の中の文字 ÷ 強調の地 |
|---|---|
| 構文色を載せる（ダーク） | 1.97 〜 4.11 |
| 構文色を載せる（ライト） | 2.04 〜 2.42 |
| **本文の色 1 色（採用）** | **4.22 / 5.47（ダーク）、9.58 / 11.38（ライト）** |

強調を暗くして構文色を残す案も測った（ダークで文字 2.99〜、強調と行の地の比は 2.23 → 1.47）。
**両方の指標で下回る**ので採らない。変わった範囲で知りたいのは「何色のトークンか」ではなく
「どこが変わったか」である。トークンの境目で切られた強調は**続きになったものを 1 つに畳む**
（角丸の継ぎ目が見えるため）。

**差分本体は仮想スクロールする**（`@tanstack/react-virtual`。コミットリストと同じ）。
**hunk の見出しも同じ行リストに入れる** — 別に描くと見出しだけが仮想化から漏れ、hunk が
数千ある差分で結局全部 DOM に載る。**行の高さは実測する**（本文を折り返すので一定でない）。
推定値は 1 行ぶんでよく、折り返す行は少数なので総高さはほとんど動かない
（6000 行で実測後の伸びは 8px）。仮想化するとブラウザの `Ctrl+F` が可視部分しか
見つけられなくなるが、これは承知の上（コミットリストも同じ）。

**折りたたみ中は行の対応付けも語単位差分もトークン化も走らせない。** DOM を作らないだけでは
重さが消えない。規模の判定（行数と UTF-8 バイト数を数えるだけ）は安いので、それだけ先に行う。
**行数とバイト数のどちらか一方でも超えたら折りたたむ** — 行数だけ見ていると、1 行が極端に
長いファイル（minify 済みなど）を素通しさせる。閾値は `settings.json` の
`ui.collapseLines` / `ui.collapseBytes`（既定 3000 行 / 500KB）。展開は**ファイルごとの
一時状態**で、永続化も持ち越しもしない（文字コードの上書きと同じ理由）。
展開後の歯止めとして、**2 万行を超える差分はハイライトしない**（トークン化は同期処理なので、
桁違いの差分を渡すとその間だけ固まる）。

**バイナリはサイズの変化を出す。** `cat-file -s` ではなく `ls-tree -l` を使う —
無いパス（追加や削除の反対側）を `cat-file` に渡すと**失敗としてログに残る**が、
`ls-tree` は空を返して成功する。**片側が無いときは `None`。0 と書くと
「空のファイルになった」に読める。** この 2 回の追加実行は**バイナリのときだけ**行う。

**`ui.contextLines` を `u8` にしてはいけない**（T-14 で発見）。画面の「すべて」は
十分大きな `-U`（1000000）で代用しているので、`u8` だと設定の保存がまるごと弾かれる。

### 7.3 コミット詳細と変更ファイル一覧

**右の列**に 2 つを縦に積み、**差分本体は中央下**に置く（§6.1）。

1. **コミット詳細**（右上） — full message / 作者・コミッター / 親 / SHA
2. **変更ファイル一覧**（右下） — 既定はフラットなパス一覧（共通ディレクトリはグレーで薄く、
   ファイル名を強調）、ディレクトリツリーに切替可。ファイルごとに +N / -M と横バー、
   ヘッダに合計
3. **選択ファイルの差分**（中央下） — 見出しにパスと状態を出す。一覧が別の列にあるので、
   どのファイルを見ているかは差分側だけで分かる必要がある

ファイル間の移動は一覧クリック ＋ `Alt+↑` / `Alt+↓`。

**取得は 1 回で、右の列と差分本体が分け合う**（`useCommitFiles`）。2 つの枝に分かれたからと
いって 2 回取りに行かないこと。
**全ファイルを縦に連結してスクロールする方式は採らない**（大きな差分で確実に重くなる）。

**一覧は 1 回の git 実行で作る。** `diff --raw --numstat -z -M` は raw 区間と numstat 区間を
1 本の NUL 列に続けて出すので、状態（A/M/D/R）とファイルモードを raw から、増減行数と
バイナリ判定を numstat から取れる。2 回呼ぶ必要はない。**リネームだけ raw も numstat も
パスを 2 つ食う**ので、そこを数え違えると以降が全部 1 件ずつずれる。

**ルートコミットは `git diff` では出せない。** 親が無いので片側を指定できず、
`diff-tree --raw --numstat -z -M --root --no-commit-id -r <sha>` を使う。
API では親を `Option<String>` にし、`None` がルートを意味する
（空ツリーの SHA を定数で埋め込む手もあるが、SHA-256 リポジトリで値が変わる）。

**バイナリの増減は `null` であって 0 ではない。** numstat が `-` を返すので、
0 行の変更と区別できるようにしておく。合計にも足さず、「バイナリ N 件」として別に数える。

**ディレクトリツリーは子が 1 つだけの連なりを 1 行にまとめる**（`src/components/diff`）。
ref ツリー（§6.4）の「3 件以上で畳む」とは規則が違う — ファイルは実際のディレクトリ構造が
そのまま意味を持つので、1 件でもディレクトリはディレクトリとして出す。
**ディレクトリの開閉は持たない**（1 コミットの変更ファイルは高々数十件で、
畳む手間より全部見えているほうが速い）。

**フラット表示で削るのはディレクトリ側だけ**にして、ファイル名は必ず残す。
`direction: rtl` で末尾を残す手は、インライン要素の並びまで反転してディレクトリが
ファイル名の後ろに出る（T-11 の目視で確認）。

**リネーム元は行内に並べず 2 行目に置く。** 右の列は 380px 程度しかないので、
パスと増減を横に並べると押し合って両方読めなくなる。

### 7.4 マージコミットの差分

マージコミットは親が 2 つあるため「差分」が一意に決まらない。`git show` の既定はマージコミットに
対して何も出さない。

- **既定は第 1 親との差分**（`git diff <merge>^1 <merge>`）
- ヘッダに親を選ぶドロップダウンを出し、明示的に第 2 親も選べる
- `--cc`（combined diff）は v1.1

**ドロップダウンはコミット詳細の見出し行に置く**（作者・親を並べた欄ではない）。
本文が長いと欄までスクロールしなければ見えず、**どの親との差分を見ているか分からないまま
一覧を読むことになる**（T-11 の目視で確認）。

**親の subject は取り直さない。** 全コミットが手元にあるので（§4.1）一覧から引く。

**選んだ親は永続化しない。** 別のコミットへ移れば意味を失う値なので、`state.json` に
残すと「前に開いたマージの第 2 親」が無関係なコミットに適用されかねない。
コミットが変わったら第 1 親へ戻す。

### 7.5 作業ツリー

**read-only 表示のみ。** stage / discard / stash は一切提供しない。

- `git status --porcelain=v2 -z` で取得し、**ステージ済み / 未ステージ / 未追跡**の 3 セクションに
  分ける。CLI 派である以上、index と working tree の区別は当然見たいものとして扱う
- **未追跡ファイルは名前を列挙し、クリックで全文表示**（差分としては見せない。全行追加の差分は
  視覚的ノイズが大きすぎる）
- 実行タイミングは**リポジトリ選択時・ウィンドウフォーカス復帰時・`F5` のみ**。
  **ファイル監視は入れない**（ビルド中のプロジェクトで大量イベントが飛ぶ）
- **コミットリスト最上部に擬似行を 1 つ置く**。この行は**レーン計算の対象外**とし、HEAD のノードへ
  点線で接続する。作業ツリーがクリーンなときはこの行を出さない

## 8. 書き込み系操作

### 8.1 checkout

- **起動点**: ブランチツリーの右クリックメニュー＋ダブルクリック、グラフ上コミットの右クリック
- **対象**: ローカルブランチ / タグ / 任意コミット。タグとコミットは detached HEAD になる旨を
  ダイアログで明示する
- **リモート追跡ブランチは detached HEAD にする。** ローカルブランチの自動作成は v1 では提供しない

  これは「git コマンドで実行するのは checkout / fetch / FF マージのみ」という宣言された制約の
  厳格解釈である。ローカルブランチ作成は ref の新規作成であり範囲外。実際のワークフロー
  （fetch → 上流の差分を見る → FF マージ）では、FF マージ対象のブランチは既にローカルに存在する
  はずで、リモート追跡ブランチの checkout は閲覧目的が主になる。閲覧目的なら detached で足りる。
  実運用で本当に不便なら v1.1 で明示的なメニュー項目として追加する

- **dirty なら事前に検出して中止**し、理由を明示する。`--force` と自動 stash は提供しない
  （ビューワーがユーザーの未保存作業を消す事故を構造的に不可能にする）

### 8.2 FF マージ

- `git merge --ff-only` 固定
- 主動線は「現在のブランチに upstream (`@{u}`) を取り込む」
- 加えて任意 ref の右クリックから「現在のブランチに FF マージ」も可
- FF 不可なら実行せず理由を表示するだけ

### 8.3 fetch

- `git fetch --all --prune --tags` 固定（ここでの `--all` は「全リモート」の意味で、§4.2 の
  `git log --all` とは別物）
- **手動のみ。定期自動 fetch は持たない。**

  自動 fetch には具体的な危険がある。認証キャッシュが切れているリモートに対して自動 fetch が
  走ると、ユーザーが何もしていないのに GCM の認証ウィンドウが突然前面に出る

- 現在のリポジトリ / 全リポジトリ一括の両方のボタンを用意
- **一括 fetch は実行前に確認ダイアログを 1 回**（対象数＋認証ウィンドウが出る可能性を明示）。
  実行中は進捗表示とキャンセル可、完了後にリポジトリごとの成功 / 失敗サマリ
- **放置警告は `.git/FETCH_HEAD` の mtime で判定する。**

  アプリ独自に記録すると、ターミナルで `git fetch` した直後にアプリが「10 日 fetch していません」と
  誤警告する。`FETCH_HEAD` の mtime なら CLI 併用でも整合が取れる。ファイルが無い＝一度も fetch
  していない、として扱う

- 閾値は既定 7 日、設定で変更可、0 で無効化
- 表示は**リポジトリ一覧行の控えめなアイコン＋ツールチップのみ**。モーダルもバナーも出さない

### 8.4 clone

- 既定ワークスペースルートを設定に持ち、`<root>/<name>` を埋めたダイアログを毎回出して確認させる
- HTTPS を主に据えつつ、SSH URL も git に素通しする
- **shallow / submodule 再帰 / ブランチ指定は提供しない**（履歴グラフが目的なので shallow は本末転倒）
- `--progress` の stderr をパースして実バー表示
- 失敗時は確認ダイアログの上で残骸ディレクトリを削除

### 8.5 書き込み後の再読込

書き込み操作の実行後は**全コミットメタ情報を再取得してレーン再計算**する。
数万コミットで 1 秒未満なので、部分更新の複雑さを持ち込まない。

## 9. 文字コード・改行・ファイル属性

閲覧対象に Linux 由来のソースが含まれる以上、ここは事故が起きる場所である。

### 9.1 文字コード

**自動判別。** UTF-8 として妥当なら UTF-8、失敗したら Shift_JIS → EUC-JP の順で試行する。
判別結果をファイルごとにステータス表示し、手動で上書き可能にする。
実装は `src-tauri/src/encoding.rs`（T-12）。

**バイナリ判定を先に行う。** 先頭 8000 バイトに NUL があればバイナリとし、デコードしない。
**範囲を git と同じにしてある** — 広げると、git が差分を出したファイルをこちらだけが
バイナリ扱いする食い違いが起きる。BOM 付き UTF-16 もここでバイナリになる（git も同じ）。

**試行は置換なしの厳密デコード**で行い、どれも通らなければ **UTF-8 の置換ありデコード**に
落として `lossy` を立てる。ASCII 部分は読めるので、この環境では最も傷が浅い。
**UTF-8 BOM は取り除いてから**判別する（残すと差分の先頭に U+FEFF が出る）。

**この方式の限界を承知で採っている。** EUC-JP のひらがなは 1 バイトずつが Shift_JIS の
半角カナとして妥当なので、**厳密デコードが通ってしまい Shift_JIS と判定される**
（`encoding.rs` の `euc_jp_hiragana_is_misdetected_as_shift_jis` が固定している）。
置換文字も出ないので、**画面に化けた半角カナが並ぶまで気付けない**。

- 直す手段は**手動上書き**である。だから上書き API を最初から持たせてある
- 統計的推定（`chardetng` 等）は v1 では入れない。判別の当たり外れが入力次第になり、
  「なぜこのファイルだけ違う結果か」を説明できなくなる。**順序なら常に説明できる**
- EUC-JP のリポジトリを常用することになったら v1.1 で再検討する

### 9.2 改行コード

- 改行コード（LF / CRLF / CR）を**ステータスバーに常時表示**
- 可視化記号はトグル（既定オフ）
- **1 ファイル内で混在したら警告アイコン**

  Linux 用シェルスクリプトに CRLF が混入すると実行時に壊れるため、目視で気づけることに実利がある

**CRLF を CR と LF に二重計上しない。** 数え方を間違えると全ファイルが「混在」になり、
警告が意味を失う。

**数え上げは渡したバイト列そのものに対して行う。** 何を渡すかは呼び出し側が決める。
**diff 出力をまるごと渡してはいけない** — ヘッダ行（`@@` や `+++`）は常に LF なので、
CRLF のファイルが全部「混在」と出る。**内容行だけを渡すこと。**

**可視化記号はサクラエディタに合わせる**（CRLF は `→↓`、LF は `↓`、CR は `→`）。
`␍␊` のような制御文字の記号は、並べてもどちらがどちらか読み取れない。
**末尾に改行が無いことだけは記号ではなく「改行なし」と書く** — 「無い」ことを表す記号は伝わらない。
こちらは可視化トグルに関わらず常に出す（差分の意味が変わるため）。

### 9.3 ファイル属性

- ファイルモード変更（`100644` → `100755`）を差分ヘッダに明示
- シンボリックリンクは「シンボリックリンク → 参照先」として明示

**どちらも `FileChange` の `oldMode` / `newMode` から出す**（`120000` がシンボリックリンク）。
差分ヘッダのために git を呼び直さない。リンク先は差分の本文にそのまま出る
（シンボリックリンクの中身はリンク先のパス 1 行）。

## 10. AI レビュー

### 10.1 プロバイダ

**OpenAI 互換 API 1 系統に統一する。** Ollama も `http://localhost:11434/v1` で受けられるため、
ネイティブ API (`/api/chat`) の別実装は持たない。`/v1/models` を叩いてモデル名を補完する。

### 10.2 プロファイル

複数保存し、レビュー実行時にドロップダウンで選択する。リポジトリごとに既定プロファイルを記憶する。

保持項目: 名前 / base URL / モデル / コンテキスト長 / temperature / max tokens。

**API キーは Windows 資格情報マネージャーに保存し、設定 JSON には参照キーのみを書く。**
設定ファイルに平文の API キーを置かない。

### 10.3 起動と比較の意味

- **主動線は「2 つのコミットを選んでレビュー」**。グラフ上で Ctrl+クリックの 2 点選択
- 比較は**既定 `git diff A B`**（2 点間のツリー差分。「コミット間の差分」の素直な解釈）、
  トグルで `git diff A...B`（マージベース起点）に切替可
- ブランチ同士の比較は v1.1
- **fetch 後の自動レビューは v1 では持たない**（コストとレイテンシがユーザー不在で発生するため）
- 作業ツリー差分もレビュー対象にできる

### 10.4 実行前パネル（必須）

- 対象ファイル一覧＋個別除外チェック
- skill の複数選択
- LLM プロファイル選択
- **概算トークン数**（文字数 ÷ 4 の粗い見積で足りる）
- コンテキスト長を超えるファイルには「hunk 分割されます」バッジ

### 10.5 投入単位

**ファイル単位で個別レビューし、最後に全体サマリを生成する。**
1 ファイルが設定トークン上限を超える場合のみ、自動で hunk 分割にフォールバックする。

差分全体を 1 リクエストにするとローカル Ollama のコンテキスト長（8k〜32k）を容易に溢れる。
逆に hunk 単位を既定にすると文脈が細切れになりレビュー品質が落ちる。

モデルに渡すのは **ファイルパス ＋ unified diff（`-U10`）＋ コミットメッセージ ＋ skill 本文**のみ。
**ファイル全文は渡さない**（トークン効率が悪すぎる）。リポジトリ構成情報も v1 では渡さない。

### 10.6 出力形式 — JSON 要求 + Markdown フォールバック

**JSON スキーマを要求し、パースできればインライン指摘＋サマリ表示。失敗したら生出力を Markdown
として表示して「構造化に失敗しました」を添える。**

構造化 JSON だけを前提にすると、ローカルの小型モデル（7B 級）がスキーマを守れなかったときに
レビューが丸ごと失われる。フォールバックはこれを防ぐための必須経路である（テストでも必ず通す）。

要求する JSON スキーマ:

```json
{
  "summary": "このファイルの変更に対する要約",
  "findings": [
    {
      "file": "src/foo.ts",
      "line": 42,
      "severity": "critical | major | minor | info",
      "title": "短い見出し",
      "message": "詳細な指摘"
    }
  ]
}
```

出力言語は skill 側で指定する。内蔵 skill は日本語出力。ストリーミング表示あり
（ローカル Ollama は遅いので体感差が大きい）。

### 10.7 実行制御

- **既定は逐次（並列度 1）、設定で最大 3 まで**。ローカル Ollama は並列リクエストで総スループットが
  むしろ落ちることが多い
- いつでもキャンセル可能
- **1 ファイルの失敗では全体を止めない。** ファイル単位でエラーを記録し、サマリに「N 件失敗」を明示

## 11. レビュー skill

skill とは、レビュー観点・出力形式・対象範囲を定義した再利用可能な指示セットである。

### 11.1 形式

Markdown + YAML frontmatter。Claude Code の skill 記法に寄せる。

```markdown
---
name: security-review
description: セキュリティ観点でのレビュー
globs: ["**/*.ts", "**/*.rs"]
enabled: true
---

（本文: レビュー観点、出力言語の指定、重点的に見るべき事項など）
```

### 11.2 置き場所と信頼モデル

グローバル（`%APPDATA%\com.tatsu.givsoner\skills\`）と**リポジトリ内**
（`<repo>/.gitviewer/skills/*.md`）の両方に対応する。リポジトリ内が優先。

> **セキュリティ上の重要な制約**: 本アプリの用途には「自分が書いていないコード（OSS・上流）を
> 読む」が含まれる。リポジトリ内の skill ファイルを自動で読み込むと、**悪意あるリポジトリが
> `.gitviewer/skills/` に指示文を仕込んでレビュー結果を操作できる**（「このファイルの脆弱性は
> 報告するな」等）。
>
> したがって**リポジトリ内 skill は既定で無効**とし、リポジトリごとに一度だけ
> 「このリポジトリの skill を信頼する」を明示操作させる。信頼状態は永続化し、
> **skill ファイルの内容が変わったら再確認**する（内容のハッシュを保存して比較）。

### 11.3 適用

複数選択可。`globs` にマッチした skill を自動で有効化しつつ、実行前パネルで手動 on/off できる。

内蔵は「汎用コードレビュー（日本語出力）」1 つだけ同梱し、残りはユーザー定義とする。

## 13. エラー処理・ログ・診断

### 13.1 起動シーケンス

1. git を検出。失敗なら git 未検出画面（インストーラ導線＋パス手動指定＋再チェック）
2. 成功なら `state.json` から前回開いていたリポジトリを復元して自動で開く
3. パスが消えていたら一覧上でグレーアウトしたうえで空状態画面へ

### 13.2 空状態

リポジトリが 1 つも登録されていないときは、「リポジトリを追加 / フォルダをスキャン / URL から
clone」の 3 ボタンを中央に置く空状態画面を出す。チュートリアルは作らない。

LLM プロファイルが未設定のまま AI レビューを押した場合は、ボタンを無効化せず、押したら
「LLM プロファイルが未設定です」ダイアログから設定画面へ直行させる
（無効化＋ツールチップは理由が伝わりにくい）。

### 13.3 ログ

- **ログファイルを書く**: `logs/givsoner-YYYY-MM-DD.log`、7 日分でローテーション。
  Phase 6 以降の認証・checkout まわりの問題は再現が難しく、後から追える記録が要る
- **画面上の git コマンドログ**は直近 500 件のリングバッファ。リポジトリ切替でクリアしない
- **Rust 側の panic はキャッチしてエラーダイアログを出し**、ログの場所を案内する

### 13.4 秘匿情報のマスキング（必須）

**出力する全文字列に対して、`://<user>:<secret>@` パターンと API キーらしき文字列を正規表現で
マスクしてから記録する。画面表示とログファイルの両方に適用する。**

`git remote -v` の出力や git の stderr には、認証情報が URL に埋まっていると平文で出る。
それをそのままログファイルに書くと `%APPDATA%` に平文トークンが残る。

実装上は、**すべてのログ出力と画面表示が単一のマスキング関数（`redact.rs`）を通る**構造にする。

---

### 13.5 白い画面を作らない

**フロントで例外が出たときに何も表示されない状態を作らない。** React は描画中に例外が出ると
木ごと外すため、受け止める場所が無いとウィンドウが真っ白になり、原因の手掛かりも残らない。
受け皿を 2 段構えで置く。

| 失敗する場所 | 受け皿 |
|---|---|
| モジュールの取得・評価（React が一度も動かない） | `index.html` のインラインスクリプト |
| 描画中の例外 | `src/components/common/ErrorBoundary.tsx` |

`index.html` 側は `error`（capture 付きで resource error も拾う）と `unhandledrejection` を見て、
`#root` が空のままなら理由を書き込む。10 秒経っても空なら「時間内に組み上がらなかった」と出す。
**この受け皿の文言だけは `src/i18n/ja.ts` に置けない**（ja.ts を読めない状況を扱うため、
インラインで持つ）。

なお、dev サーバ自体に到達できない場合（`npm run dev` が立っていない、ポート 1420 が別プロセスに
取られている）は HTML すら配信されないので、この受け皿も動かない。WebView2 のエラーページか
白い画面になる。`tauri dev` の出力に `Port 1420 is already in use` が出ていないか先に見ること。

---

**アプリ側で手当てできない白画面が 1 つある。** フィルタリング系ソフトが WebView2 の
ページに content script を差し込む場合、その問い合わせが返るまでページの評価が止まる。
実測（AdGuard 8.0.5560.0）では `injections.adguard.org` への要求が 29 秒返らず、
その間 `index.html` のインラインスクリプトすら動かなかった（HTML 自体は 33ms で届いていた）。
**受け皿は「自分のコードが動き始めた後」しか守れない**ので、これは環境側で外すしかない
（CLAUDE.md §10）。原因の切り分けには WebView2 のリモートデバッグが使える:
`WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS=--remote-debugging-port=9222` を付けて起動し、
`http://127.0.0.1:9222/json` でページの状態を見て、CDP で
`performance.getEntriesByType("resource")` を取る。

## 14. テスト戦略

### 14.1 レーン割り当てアルゴリズム（必須）

このアプリの心臓部であり、かつ目視デバッグが最も辛い部分（グラフが崩れても「なんとなく変」としか
分からない）なので、テストの投資対効果が突出して高い。

手書き DAG フィクスチャで期待レーン配列を検証する。最低限のケース:

- 直線的な履歴
- 単純な分岐と合流
- 連続するマージ
- オクトパスマージ（親が 3 つ以上）
- ルートコミットが複数ある履歴
- **lane 0 の幹予約が守られること**
- **可視 ref を絞ったときの再計算が正しいこと**

### 14.2 git 出力パーサ（必須）

実際の `git` 出力を固定文字列として持つ。異常系を必ず含める:

- 日本語ファイル名
- 空の subject
- 複数親
- 署名付きコミット
- 改行を含む subject

### 14.3 結合テスト

テスト用リポジトリを**シェルスクリプト（または Rust）で生成**する。
手元の実リポジトリには依存しない（CI で再現可能にする）。

実体は `scripts/make-test-repos.sh`（T-02 で作成）。テストは `src-tauri/tests/` に置く。
**生成する形はスクリプト先頭のコメントが一覧**（直線 / 分岐と合流 / 連続マージ /
オクトパス / ルート 2 つ / 合流しない orphan / 日本語名 / 空 subject / コミット 0 件 /
detached / 複数行メッセージ / タグ / bare / クローン / 上流と分岐したクローン）。
形を足すときはスクリプトとコメントの両方に足し、`tests/lanes.rs` の一覧にも入れる。

- 生成先は **`%TEMP%\givsoner-test-repos`**。この gitviewer リポジトリの中に置くと、
  「リポジトリでないパス」の判定テストが親リポジトリを拾って落ちる。
- Windows では **git 付属の bash（`<Git>\bin\bash.exe`）で実行する**。PATH 上の `bash` は
  WSL のことがあり、Windows のパスを渡しても解決できない。`GIT_BASH` で明示指定もできる。
- msys の bash へ渡す引数はスラッシュ区切りにする（`\` がエスケープとして食われる）。
- `src-tauri/src` の中では `Command::new` を git 以外に使わない（§3.1 のチョークポイント）。
  プロセス起動を伴うテスト補助は `src-tauri/tests/` 側に書く。

- 署名付きコミットだけは生成しない（CI に GPG 鍵を置けない）。署名は `--format` の出力形状を

## 付録 A. 使用する git コマンド一覧

すべて §3.1 の固定オプションと §3.2 の環境変数を付けて実行する。

| 用途 | コマンド |
|---|---|
| バージョン検出 | `git --version` |
| リポジトリ判定 | `git -C <path> rev-parse --absolute-git-dir --is-bare-repository --is-shallow-repository` |
| 作業ツリーの場所 | `git -C <path> rev-parse --show-toplevel`（bare では呼ばない） |
| **コミットメタ一括取得** | `git -C <path> log --branches --remotes [HEAD] --topo-order -z --format=<fmt>` |
| ref 一覧 | `git -C <path> for-each-ref --format=<fmt> refs/heads refs/remotes refs/tags` |
| HEAD 判定 | `git -C <path> symbolic-ref -q --short HEAD` / `git -C <path> rev-parse -q --verify HEAD` |
| 作業ツリー状態 | `git -C <path> status --porcelain=v2 -z` |
| コミット本文 | `git -C <path> show -s --format=<fmt> <sha>` |
| 変更ファイル一覧 | `git -C <path> diff --numstat -z -M <A> <B>` |
| ファイル差分 | `git -C <path> diff -M -U<N> [-w] <A> <B> -- <path>` |
| ステージ済み差分 | `git -C <path> diff -M -U<N> --cached` |
| 未ステージ差分 | `git -C <path> diff -M -U<N>` |
| ファイルツリー | `git -C <path> ls-tree -z -r <rev>` |
| ファイル内容 | `git -C <path> show <rev>:<path>` |
| fetch | `git -C <path> fetch --all --prune --tags --progress` |
| checkout | `git -C <path> checkout <ref>` / `git -C <path> checkout --detach <sha>` |
| FF マージ | `git -C <path> merge --ff-only <ref>` |
| clone | `git clone --progress <url> <dir>` |

ahead/behind は git を呼ばずメモリ上のグラフから計算する（§4.5）。

**`<fmt>` の書式言語はコマンドごとに違う。** `git log` は `%x1f`（`%x` ＋ 16 進 2 桁）で
区切り文字を出すが、`for-each-ref` は `%x1f` を展開せず、16 進 2 桁だけの `%1f` を使う
（git 2.43 で実測）。取り違えると、区切りのつもりの `%x1f` が文字列のまま出力に混ざる。

**`git log` に `HEAD` を渡すのは HEAD がコミットを指しているときだけ。** コミット 0 件の
リポジトリに渡すと `fatal: ambiguous argument 'HEAD'` でコマンド全体が失敗する。
`--branches --remotes` だけなら exit 0 で空が返る。

**`refs/remotes/origin/HEAD` は `for-each-ref` の `%(symref)` で拾う**ため、`symbolic-ref` を
別に呼ばない。symbolic ref を ref 一覧から外さないと、`origin/main` がブランチとして二重に見える。
